# Задание 1. Потерянные инкременты

## Теория
- **Поток** — отдельный путь выполнения внутри одного процесса. Потоки имеют общую память, поэтому могут одновременно обращаться к одним и тем же полям.
- **Состояние гонки (race condition)** — ситуация, когда результат зависит от порядка доступа потоков к общим данным.
- `counter++` — это не атомарная операция, а три шага: прочитать значение, вычислить новое, записать его обратно.
- Если два потока прочитали одно и то же значение, оба могут записать одинаковый результат. Одно увеличение потеряется.
- **Атомарность** означает, что операция выполняется как единое целое и другие потоки не видят её промежуточное состояние.
- `synchronized` обеспечивает взаимное исключение: в критическую секцию одновременно входит только один поток.
- У каждого объекта есть **монитор**. `synchronized`-метод использует монитор `this`, а `synchronized`-блок — монитор указанного объекта.
- `synchronized` также обеспечивает **видимость**: изменения, сделанные до выхода из блока, видны потоку, который затем вошёл в тот же монитор.
- `volatile` обеспечивает видимость, но не делает `counter++` атомарным, поэтому для счётчика его недостаточно.
- Инвариант корректного счётчика: после `N` потоков по `K` инкрементов значение должно быть равно `N * K`.

### Демонстрация
Вывод программы:
```
=== Задание 1. Потерянные инкременты ===
Ожидаемое значение: 320000
Без синхронизации: 75865 (потеряно 244135)
synchronized-метод: 320000
synchronized-блок: 320000
```
Объяснение вывода: 16 потоков по 20 000 раз увеличивали общий счётчик. Без синхронизации часть операций перезаписала результаты друг друга, поэтому итог оказался меньше `320000`. Точное число потерянных инкрементов зависит от планировщика и при каждом запуске может быть разным. Варианты с `synchronized`-методом и `synchronized`-блоком дали ожидаемое значение. В коде есть `UnsafeCounter` с обычным `value++` и `StepCounter`, где то же самое разложено явно: `current = value`, `next = current + 1`, `value = next`. Unit-тест `Task1LostIncrementTest` выполняет несколько раундов и проверяет, что оба небезопасных варианта хотя бы в одном раунде теряют инкременты, а синхронизированные варианты всегда точны.

#### Правило
Если несколько потоков изменяют общее составное значение, защищайте всю операцию целиком через `synchronized`, `Lock` или атомарный тип. Одного `volatile` для `counter++` недостаточно.

# Задание 2. Флаг остановки и видимость

## Теория
- **Видимость** — гарантия того, что изменение переменной одним потоком станет заметно другому потоку.
- Без синхронизации поток может читать закэшированное значение и не увидеть, что другой поток изменил флаг.
- `volatile` гарантирует, что запись сразу станет видимой другим потокам, а чтение увидит последнюю запись.
- `volatile` также запрещает переупорядочивание операций через `volatile`-обращение.
- `volatile` не делает составные операции атомарными: `volatile int count; count++` по-прежнему содержит гонку.
- Для одного независимого флага «работать/остановиться» `volatile` подходит: с ним выполняются только атомарные чтение и запись.
- Альтернатива — обычное поле с синхронизированными getter/setter. Тогда видимость обеспечивает монитор, но появляется цена блокировки.
- `interrupt()` — дополнительный механизм: он помогает разбудить поток, если тот ждёт или блокируется.
- В тестах для ожидания старта и остановки лучше использовать `CountDownLatch`, а не `Thread.sleep`: защёлка ждёт событие, а не время.

### Демонстрация
Вывод программы:
```
=== Задание 2. Флаг остановки ===
Worker запущен, флаг остановки пока false
Worker остановлен, итераций: 376
```
Объяснение вывода: Worker работал в цикле `while (!stop)`. После вызова `stop()` поле `stop` стало `true`, и благодаря `volatile` worker увидел новое значение и завершил цикл. Количество итераций зависит от скорости машины и не является проверяемым результатом. Некорректный вариант — то же поле без `volatile`, из-за которого поток может никогда не увидеть остановку. Отдельный тест на такой вариант не добавлен намеренно: модель памяти Java не гарантирует, что отсутствие `volatile` всегда приводит к зависанию, поэтому тест был бы нестабильным. Unit-тест `Task2StopFlagTest` подтверждает старт и завершение исправленного worker через защёлки.

#### Правило
Для одиночного флага остановки используйте `volatile`. Если с переменной выполняются составные операции или она связана с другими полями, используйте `synchronized` или атомарные классы.

# Задание 3. Реестр активных сессий

## Теория
- `HashMap` не безопасен для одновременного изменения из нескольких потоков: возможны потеря данных и повреждение структуры.
- `ConcurrentHashMap` рассчитан на конкурентный доступ и обычно не блокирует всю таблицу целиком.
- `putIfAbsent(key, value)` атомарно проверяет отсутствие ключа и вставляет значение.
- `putIfAbsent` возвращает `null`, если ключа не было и значение вставлено. Если ключ уже был, возвращается существующее значение.
- Связка `containsKey` + `put` неатомарна: между проверкой и вставкой другой поток может успеть создать запись.
- В `ConcurrentHashMap` нельзя хранить `null` ни в ключах, ни в значениях.
- `size()` у конкурентной коллекции во время изменений является оценкой, а не «замороженным» числом.
- `Map.copyOf` создаёт независимую неизменяемую копию для безопасного чтения.
- `Optional` в результате поиска заставляет явно обработать отсутствие сессии.

### Демонстрация
Вывод программы:
```
=== Задание 3. Реестр активных сессий ===
Первое создание: true
Повторное создание: false
Активных сессий: 1
Найденная сессия: ActiveSession[sessionId=1, studentId=101, courseCode=JAVA-101]
```
Объяснение вывода: Первый вызов `createIfAbsent` вставил сессию и получил от `putIfAbsent` значение `null`, поэтому вернул `true`. Второй вызов обнаружил существующий ключ и вернул `false`. В реестре осталась одна сессия. Unit-тест `Task3SessionRegistryTest` дополнительно запускает 12 потоков, которые одновременно создают сессию с одним `sessionId`; успешным оказывается ровно один вызов.

#### Правило
Для атомарного создания «только если отсутствует» используйте `putIfAbsent` или `computeIfAbsent` в `ConcurrentHashMap`, а не отдельные `containsKey` и `put`.

# Задание 4. Producer–consumer на BlockingQueue

## Теория
- **Producer–consumer** разделяет создание задач и их обработку через очередь.
- **Ограниченная очередь** не позволяет производителям бесконечно обгонять потребителей и ограничивает объём данных в памяти.
- `BlockingQueue.put` блокируется, если очередь заполнена. Это создаёт **backpressure**: producer ждёт, пока consumer освободит место.
- `BlockingQueue.take` блокируется, если очередь пуста. Consumer не крутит цикл вхолостую и не тратит CPU на busy waiting.
- **Poison pill** — специальное сообщение, которое говорит consumer завершиться. Нужен отдельный сигнал на каждого consumer.
- `ExecutorService` управляет пулом потоков и завершением задач.
- Для **CPU-bound** задач ориентир размера пула — число доступных процессоров. Лишние потоки добавят переключения контекста.
- Для **blocking**-сценария потоков обычно нужно больше, потому что часть из них ждёт `take`, `put`, I/O или блокировку.
- `ThreadFactory` позволяет задать понятные имена потоков для логов и диагностики.
- `shutdown()` запрещает новые задачи, но даёт уже отправленным завершиться.
- `awaitTermination` ждёт фактического завершения ограниченное время.
- `shutdownNow()` прерывает потоки и возвращает задачи, которые не начали выполняться.
- Ошибку producer нельзя молча терять: в коде она сохраняется в `AtomicReference` и после ожидания producers пробрасывается вызывающему коду.

### Демонстрация
Вывод программы:
```
=== Задание 4. Producer-consumer ===
Обработано заявок: 12
Worker-потоки: [enrollment-worker-3, enrollment-worker-4, enrollment-worker-5]
```
Объяснение вывода: 12 заявок были разложены в ограниченную очередь двумя producers и обработаны тремя consumers. Все заявки дошли до обработки, потому что `put` ждал освобождения места, а `take` ждал появления заявки. После завершения producers каждый consumer получил свой poison pill. Номера и порядок worker-потоков могут отличаться, это нормально для конкурентной программы. Если producer завершился с `RuntimeException`, ошибка не теряется: она сохраняется в `AtomicReference`, а после `producersDone.await` пробрасывается из `process`. Unit-тест `Task4EnrollmentPipelineTest` проверяет, что 200 заявок обработаны ровно один раз и что все результаты получены из потоков с префиксом `enrollment-worker-`.

#### Правило
Для producer–consumer используйте ограниченную `BlockingQueue` с блокирующими `put`/`take`, а для завершения отправляйте poison pill по числу consumers. Executor всегда завершайте через `shutdown`, `awaitTermination` и, при необходимости, `shutdownNow`.

# Задание 5. Детерминированный тест гонки

## Теория
- **Детерминированный конкурентный тест** управляет ключевыми событиями и проверяет инвариант, а не полагается на случайное расписание потоков.
- `CountDownLatch` — одноразовая защёлка. Потоки уменьшают счётчик, а ожидающие ждут, пока он станет нулём.
- Две защёлки удобны для схемы теста:
  - `ready` — все потоки подготовились;
  - `start` — всем разрешено начать одновременно.
- `CyclicBarrier` тоже задаёт точку встречи, но его можно использовать повторно. `Phaser` поддерживает фазы и гибкое управление участниками.
- `@Timeout` в JUnit не даёт тесту зависнуть навсегда.
- `Future.get(timeout, unit)` ограничивает ожидание результата конкретной задачи.
- `Thread.sleep` не является синхронизацией: он не гарантирует, что другой поток успел выполнить нужное действие.
- Executor нужно освобождать в `finally`, даже если проверка упала.
- `shutdownNow` прерывает задачи, которые ещё ждут старта или результата.

### Демонстрация
Тест `Task5DeterministicRaceTest` не печатает вывод, а проверяет инварианты:
```
потоков: 16
одновременных вызовов createIfAbsent: 16
успешных созданий: 1
активных сессий: 1
```
Объяснение: все 16 задач сначала уменьшают `ready`, затем ждут `start`. Основной поток дожидается `ready`, после чего вызывает `start.countDown()`. Все потоки одновременно пытаются создать одну и ту же сессию, но `putIfAbsent` пропускает только одного. Тест проверяет, что успешным оказался ровно один вызов, а в реестре осталась одна сессия. В `finally` executor освобождается через `shutdownNow`, поэтому даже при ошибке тест не оставит живые потоки.

#### Правило
Для конкурентных тестов управляйте стартом через `CountDownLatch`/`CyclicBarrier`/`Phaser`, добавляйте `@Timeout` и всегда освобождайте executor в `finally`. Не используйте `Thread.sleep` как синхронизацию.

# Задание 6. Ёмкость курса при конкурентной записи

## Теория
- **Ёмкость (capacity)** — максимальное число студентов на курсе.
- Инварианты конкурентной записи: успешных записей не больше capacity; один студент не занимает место дважды; отказ не меняет итоговое состояние.
- **Coarse-grained lock** — одна грубая блокировка на весь метод. Она проста и корректна, но все записи сериализуются.
- **Атомарные операции** (`AtomicInteger`, `incrementAndGet`, `compareAndSet`) позволяют обновлять отдельные значения без общей блокировки.
- **Concurrent collections** (`ConcurrentHashMap.newKeySet`) дают безопасные конкурентные операции над коллекцией.
- Атомарность отдельной операции не делает атомарной всю бизнес-операцию из нескольких шагов.
- В варианте с `AtomicInteger` и конкурентным множеством место резервируется CAS-циклом: счётчик никогда не превышает capacity. Если места нет, ранее добавленный студент удаляется.
- `synchronized`-вариант проще: проверка дубликата, проверка capacity и вставка выполняются под одним монитором.
- Атомарный вариант лучше масштабируется, но сложнее в сопровождении и требует аккуратного тестирования итоговых инвариантов.

### Демонстрация
Вывод программы:
```
=== Задание 6. Ёмкость курса ===
synchronized + HashSet: capacity=5, успешных зачислений=5, записано=5
AtomicInteger + ConcurrentHashMap: capacity=5, успешных зачислений=5, записано=5
```
Объяснение вывода: 20 потоков пытались записаться на курс с capacity 5. В обоих вариантах успешными оказались ровно 5 зачислений, и в итоговом состоянии также осталось 5 студентов. Unit-тест `Task6CapacityEnrollmentTest` проверяет оба варианта при 64 попытках в 16 потоках, отдельно проверяет дубликат одного студента и неизменность состояния после отказа.

#### Правило
При конкурентном изменении ограниченного ресурса проверяйте не только отсутствие переполнения, но и уникальность, и неизменность состояния после отказа. Для простоты выбирайте `synchronized`, для масштабируемости — атомарные операции и concurrent collections с CAS-резервированием и корректным откатом.
