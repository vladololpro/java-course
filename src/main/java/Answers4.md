# Задача 1. String: identity и value

## Теория
- В Java строки неизменяемы. Оператор `==` сравнивает ссылки (адреса в памяти), а метод `equals` сравнивает сами символы.
- Конкатенация - это склеивание строк через знак `+`. Если склеиваются строки в кавычках (литералы), компилятор делает это сразу при сборке программы (compile-time). Если склеиваются переменные, склеивание происходит во время работы программы (runtime), и создается новый объект в памяти.
- String Pool (пул строк) - это специальный склад строк в памяти. Когда мы пишем строку в кавычках, Java проверяет, есть ли такая на складе. Если есть, возвращает ссылку на нее, чтобы не тратить память.
- Метод `intern()` позволяет принудительно положить строку на этот склад (или найти уже существующую там) и получить ссылку на нее.

### Демонстрация
Вывод программы:
```
=== 1. Литералы и == ===
s1 == s2: true
s1.equals(s2): true

=== 2. new String ===
s1 == s3: false
s1.equals(s3): true

=== 3. Конкатенация compile-time ===
s1 == s4: true
s1.equals(s4): true

=== 4. Конкатенация runtime ===
s1 == s5: false
s1.equals(s5): true

=== 5. intern ===
s1 == s6: true
```
Объяснение вывода:
1. Литералы: обе строки ищутся в пуле, находят одну и ту же, поэтому ссылки одинаковые (`true`).
2. `new String`: принудительно создает новый объект в куче, адрес другой (`false`), но символы те же (`equals` дает `true`).
3. Compile-time конкатенация: компилятор склеивает константы "Ja" и "va" прямо в коде в одну строку "Java", которая попадает в пул, поэтому `==` дает `true`.
4. Runtime конкатенация: склейка переменных создает новый объект в куче, адрес другой (`false`).
5. `intern`: переносит строку из кучи в пул и возвращает ссылку на пуловский вариант, поэтому `==` с изначальным литералом дает `true`.

#### Правило
Текст в Java сравнивается только через `equals()` (или `Objects.equals()` для защиты от null). Оператор `==` для строк использовать нельзя, кроме проверки на null.

# Задача 2. Сборка строки

## Теория
- В Java строки неизменяемы (immutable). Если мы "меняем" строку, на самом деле каждый раз создается абсолютно новый объект в памяти. Старый объект становится мусором.
- Конкатенация через `+` в цикле работает очень медленно, потому что на каждой итерации создается новая строка, куда перекопируется все предыдущее содержимое. Чем длиннее строка, тем дольше копирование.
- `StringBuilder` - это изменяемый буфер. Он хранит массив символов. При добавлении текста (`append`) он просто дописывает символы в конец массива. Когда буфер заполняется, он расширяется. В конце мы вызываем `toString()`, и создается одна итоговая строка.
- Разница в скорости становится огромной при больших объемах данных.

### Демонстрация
Вывод программы:
```
=== Сборка через + ===
Время: 163 мс
Длина строки: 98890

=== Сборка через StringBuilder ===
Время: 1 мс
Длина строки: 98890

Результаты идентичны: true
```
Объяснение вывода:
1. Сборка через `+` заняла 163 мс, потому что на каждой из 10000 итераций создавалась новая строка и копировались все предыдущие символы.
2. Сборка через `StringBuilder` заняла 1 мс, потому что символы просто добавлялись в конец внутреннего массива без пересоздания объекта.
3. Обе строки получились одинаковой длины (98890) и идентичны по содержанию (`equals` дает `true`), разница только в затраченном времени.

#### Правило
Для сборки или изменения строк в цикле (или при множественных операциях) всегда используется `StringBuilder`. Оператор `+` подходит только для простых склеек в одну строку (например, `String s = a + b;`).

# Задача 3. Регулярное выражение с группами

## Теория
- Регулярные выражения в Java используются для проверки строк по шаблону. Главные классы: `Pattern` (компилирует шаблон) и `Matcher` (применяет его к строке).
- Круглые скобки `()` в регулярном выражении создают группы. Это позволяет потом извлечь нужные части строки отдельно (например, префикс и число).
- Метод `matches()` проверяет, совпадает ли шаблон со строкой целиком от начала до конца. Это защищает от частичных совпадений (когда в строке есть лишние символы до или после).
- Шаблон `[A-Z]{2,4}` ищет от 2 до 4 заглавных латинских букв. Пробелы, кириллица и строчные буквы под этот шаблон не подходят.
- `\d{3}` ищет ровно три цифры.

### Демонстрация
Вывод программы:
```
=== Валидные коды ===
OK: "JAVA-101" -> prefix=JAVA, number=101
OK: "CS-999" -> prefix=CS, number=999
OK: "WEB-001" -> prefix=WEB, number=001

=== Невалидные коды ===
FAIL: "java-101" (невалидный)
FAIL: "JAVA101" (невалидный)
FAIL: "JAVA-10" (невалидный)
FAIL: "JAVA-101!" (невалидный)
FAIL: " JAVA-101" (невалидный)
FAIL: "JAVA-101 " (невалидный)
FAIL: "ПРОГ-101" (невалидный)
FAIL: "TOOLONG-101" (невалидный)
```
Объяснение вывода:
1. Валидные коды (`JAVA-101`, `CS-999`, `WEB-001`) полностью соответствуют шаблону. `Matcher.matches()` возвращает `true`, а через `matcher.group(1)` и `matcher.group(2)` извлекаются префикс и число.
2. Строчные буквы (`java-101`) не подходят под `[A-Z]`, так как шаблон требует заглавные.
3. Отсутствие дефиса (`JAVA101`) или недостаточное количество цифр (`JAVA-10`) нарушают структуру.
4. Лишние символы (`JAVA-101!`) или пробелы (` JAVA-101`) приводят к тому, что `matches()` возвращает `false`, потому что строка не совпадает целиком.
5. Кириллица (`ПРОГ-101`) и слишком длинный префикс (`TOOLONG-101`) не проходят из-за строгого ограничения `{2,4}` и диапазона `A-Z`.

#### Правило
Для строгой проверки формата строки всегда используется `matches()` (или добавляются якоря `^` и `$` при использовании `find()`). Группы `()` позволяют удобно извлекать части данных из валидной строки.

# Задача 4. Autoboxing и null

## Теория
- В Java есть примитивы (`int`, `double`) и классы-обертки (`Integer`, `Double`).
- **Autoboxing** — автоматическое превращение примитива в обертку (например, `Integer x = 5;`).
- **Unboxing** — автоматическое превращение обертки обратно в примитив (например, `int y = x;`).
- Если переменная типа `Integer` равна `null`, при попытке использовать ее как примитив (например, сложить) возникает `NullPointerException` (NPE).
- Java кэширует объекты `Integer` для значений от **-128 до 127**. В этом диапазоне `==` возвращает `true` (ссылки на один объект). Вне диапазона (например, 1000) создаются разные объекты, и `==` возвращает `false`.
- Опираться на кэш оберток нельзя — это внутренняя деталь реализации.
- Для сравнения значений оберток всегда используется `equals()`. Перед unboxing всегда проверяем на `null`.

### Демонстрация
Вывод программы:
```
=== 1. Кэш Integer (от -128 до 127) ===
Integer a = 100, b = 100
a == b: true
a.equals(b): true

Integer c = 1000, d = 1000
c == d: false
c.equals(d): true

=== 2. NullPointerException при unboxing ===
Поймали NPE! Переменная была null.

=== 3. Правильный контракт ===
safe is null, избежали NPE.

=== 4. Правильное сравнение оберток ===
x и y равны по значению (использован equals).
```
Объяснение вывода:
1. Число 100 попадает в кэш `Integer` (от -128 до 127), поэтому `a == b` дает `true` (ссылки одинаковые).
2. Число 1000 выходит за пределы кэша, создаются два разных объекта в куче, поэтому `c == d` дает `false`, хотя `equals` говорит `true` (значения равны).
3. При попытке сложить `null` с числом Java пытается сделать unboxing и бросает NPE.
4. Явная проверка `safe != null` предотвращает вызов unboxing для пустой ссылки, и программа продолжает работу.
5. Для сравнения оберток правильно использовать `equals()`, который смотрит на значения, а не на адреса в памяти.

#### Правило
Никогда не полагайтесь на `==` для сравнения классов-оберток и на их кэширование. Всегда используйте `equals()` и проверяйте на `null` перед выполнением арифметических операций.

# Задача 5. BigDecimal без сюрприза double

## Теория
- Типы `double` и `float` хранят числа в двоичном формате. Некоторые десятичные дроби (например, 0.1) невозможно точно представить в двоичной системе, поэтому возникает погрешность.
- Из-за этой погрешности `0.1 + 0.2` может дать результат `0.30000000000000004`. Для инженерных задач это не страшно, но для финансовых расчетов это недопустимо.
- Класс `BigDecimal` предназначен для точных вычислений. Он хранит число как целое значение и масштаб (количество знаков после запятой).
- Создавать `BigDecimal` можно тремя способами:
  1. `new BigDecimal(0.1)` - **плохой способ**. Передается уже испорченный `double`, и в `BigDecimal` сохраняется вся двоичная погрешность.
  2. `BigDecimal.valueOf(0.1)` - **хороший способ**. Внутри `double` превращается в строку, а затем в `BigDecimal` без потери точности.
  3. `new BigDecimal("0.1")` - **идеальный способ**. Передается строка, класс парсит ее точно.
- Для сложения, вычитания, умножения и деления в `BigDecimal` используются методы `add()`, `subtract()`, `multiply()`, `divide()`. Обычные операторы `+`, `-`, `*`, `/` для объектов не работают.

### Демонстрация
Вывод программы:
```
=== 1. Создание BigDecimal ===
new BigDecimal(0.1): 0.1000000000000000055511151231257827021181583404541015625
BigDecimal.valueOf(0.1): 0.1
new BigDecimal("0.1"): 0.1

=== 2. Расчет стоимости трех курсов ===
Стоимость 1: 199.99
Стоимость 2: 299.99
Стоимость 3: 149.99
Итого: 649.97

=== 3. Ловушка double ===
0.1 + 0.2 = 0.30000000000000004
(Для сравнения через BigDecimal: 0.3)
```
Объяснение вывода:
1. `new BigDecimal(0.1)` показал длинную "мусорную" строку, потому что `double` уже содержал погрешность, и `BigDecimal` честно ее сохранил.
2. `BigDecimal.valueOf(0.1)` и `new BigDecimal("0.1")` дали точное `0.1`.
3. При сложении трех курсов через `BigDecimal` получился точный результат `649.97`, без копеечных расхождений.
4. Операция `0.1 + 0.2` на обычных `double` дала `0.30000000000000004` (погрешность), а `BigDecimal` дал точный `0.3`.

#### Правило
Для работы с деньгами и точных расчетов всегда используется `BigDecimal`. Никогда не создавайте `BigDecimal` из `double` (только из `String` или через `valueOf`). Для сравнения `BigDecimal` используйте метод `compareTo()`, так как `equals()` сравнивает еще и точный масштаб (например, `0.1` и `0.10` через `equals` не равны).

# Задача 6. Масштаб и округление

## Теория
- Масштаб (scale) - это количество знаков после запятой в `BigDecimal`. Числа `100.5` (масштаб 1) и `100.50` (масштаб 2) имеют одинаковое значение, но разный масштаб.
- При изменении масштаба (`setScale` или `divide`) обязательно указывается режим округления (`RoundingMode`), чтобы Java знала, как отбрасывать лишние цифры.
- Основные режимы: `HALF_UP` (обычное математическое округление), `DOWN` (отбрасывание), `HALF_EVEN` (банковское).
- При распределении денег (например, скидки) возникает проблема: если разделить сумму поровну и округлить каждую часть, общая сумма может не сойтись с исходной из-за потери копеек при округлении.
- Алгоритм сходимости: сначала делим сумму с округлением вниз (`DOWN`), затем считаем остаток (разницу между исходной суммой и суммой округленных частей) и добавляем этот остаток к одной из позиций (например, к первой). Так итог всегда сходится.

### Демонстрация
Вывод программы:
```
=== Распределение скидки 10.00 на 3 позиции ===
Позиция 1: скидка 3.34
Позиция 2: скидка 3.33
Позиция 3: скидка 3.33
Сумма скидок: 10.00
Ожидалось:   10.00
Совпадает:   true
```
Объяснение вывода:
1. Скидка `10.00` делится на 3 позиции. Без остатка не делится.
2. Базовая часть: `10.00 / 3 = 3.333...`. Округляем вниз (`RoundingMode.DOWN`) до 2 знаков, получаем `3.33`.
3. Три позиции по `3.33` в сумме дают `9.99`. Остаток: `10.00 - 9.99 = 0.01`.
4. Этот остаток `0.01` добавляется к первой позиции. Получается: `3.34`, `3.33`, `3.33`.
5. Сумма: `3.34 + 3.33 + 3.33 = 10.00`. Совпадает с ожидаемой (`true`).

#### Правило
При распределении денег между позициями всегда нужно явно указывать режим округления. Если сумма частей не сходится с ожидаемой из-за копеек, остаток нужно детерминированно добавлять к одной из позиций, чтобы итог сошелся.

# Задача 7. Math и воспроизводимая случайность

## Теория
- Компьютеры генерируют не истинно случайные, а псевдослучайные числа. Для старта алгоритма используется начальное значение — `seed` (зерно).
- Если создать генератор с конкретным `seed` (например, `new Random(42)`), он будет выдавать одинаковую последовательность чисел при каждом запуске программы. Это называется детерминированностью и критически важно для тестов.
- Если создать генератор без `seed` (`new Random()`), Java берет текущее время. Числа будут разными при каждом запуске (production режим).
- Для получения числа в заданном диапазоне `[min, max]` используется формула: `min + generator.nextInt(max - min + 1)`. Метод `nextInt(bound)` возвращает число от `0` до `bound - 1`.
- Интерфейс `RandomGenerator` (Java 17+) объединяет разные реализации случайных генераторов (`Random`, `SplittableRandom` и др.).
- Класс `Math` содержит статические методы: `abs` (модуль), `round` (округление до целого), `ceil` (вверх), `floor` (вниз).

### Демонстрация
Вывод программы:
```
=== 1. Тестовый источник (детерминированный) ===
Test (seed=42): [76, 95, 50, 79, 59]

=== 2. Тестовый источник (повторный запуск) ===
Test (seed=42) повторно: [76, 95, 50, 79, 59]

=== 3. Production источник (случайный) ===
Production (без seed): [68, 90, 71, 59, 91]

=== 4. Математические функции ===
Math.abs(-5.5) = 5.5
Math.round(-5.5) = -5
Math.ceil(-5.5) = -5.0
Math.floor(-5.5) = -6.0
```
Объяснение вывода:
1. Первые два блока с `seed=42` выдали абсолютно одинаковые числа, потому что алгоритм стартовал с одного и того же зерна.
2. Третий блок без `seed` выдал другие числа, так как зерно было инициализировано текущим временем.
3. `Math.abs(-5.5)` вернул `5.5` (модуль).
4. `Math.round(-5.5)` вернул `-5`, так как в Java `round` округляет к ближайшему целому, а `-5.5` находится ровно посередине — округление идет в сторону плюса (к -5).
5. `Math.ceil(-5.5)` вернул `-5.0` (вверх, к большему целому).
6. `Math.floor(-5.5)` вернул `-6.0` (вниз, к меньшему целому).

#### Правило
Для тестов всегда используйте генератор с фиксированным `seed` (детерминированность). Для production — без `seed` (случайность). Для математических операций встроенные методы `Math` покрывают базовые потребности.

# Задача 8. LocalDate и календарные правила

## Теория
- Пакет `java.time` (появился в Java 8) используется для работы с датами. Главный класс для даты без времени — `LocalDate`.
- Объекты `LocalDate` **неизменяемы**. Методы вроде `plusDays()` или `plusWeeks()` не меняют исходный объект, а возвращают **новый**. Поэтому результат всегда нужно присваивать в переменную.
- `LocalDate.of(год, месяц, день)` создает дату. `plusWeeks(n)` добавляет недели, `minusDays(n)` отнимает дни.
- Метод `isLeapYear()` проверяет, является ли год високосным. Високосный год делится на 4, но не на 100, либо делится на 400 (например, 2024, 2000).
- `getDayOfWeek()` возвращает день недели (например, `SUNDAY`).
- Прибавление недель может перевести дату в следующий год (например, декабрь + 8 недель = февраль следующего года).

### Демонстрация
Вывод программы:
```
=== 1. Начало модулей ===
Модуль 1: 2024-09-02
Модуль 2: 2024-10-28
Модуль 3: 2024-12-23

=== 2. Неизменяемость ===
Исходная дата: 2024-09-02
После plusDays(10): 2024-09-12
Исходная осталась прежней: true

=== 3. Последний учебный день ===
Начало модуля 3: 2024-12-23
Конец модуля 3: 2025-02-16
День недели конца: SUNDAY

=== 4. Високосный год ===
2024 високосный: true (29 февраля существует)
2023 високосный: false
2000 високосный: true
1900 високосный: false
```
Объяснение вывода:
1. Начало модулей рассчитывается прибавлением 8 недель (56 дней) к предыдущей дате. Третий модуль начинается 23 декабря 2024 года.
2. При вызове `plusDays(10)` исходная дата не изменилась (осталась 2 сентября), а новая переменная стала 12 сентября. Это доказывает неизменяемость `LocalDate`.
3. Конец третьего модуля (через 8 недель минус 1 день) перешел на следующий год — 16 февраля 2025 года (это воскресенье).
4. 2024 год делится на 4 и не делится на 100, поэтому он високосный (`true`). 2023 не делится на 4 (`false`). 2000 делится на 400 (`true`). 1900 делится на 100, но не на 400 (`false`).

#### Правило
Для работы с датами используется `LocalDate`. Все методы возвращают новый объект, не меняя исходный. Для расчета дат всегда присваивайте результат: `newDate = oldDate.plusWeeks(1)`.
