# Практика 10. Асинхронные вычисления и современная конкурентность

## Задание 1. `Callable` и `Future`

### Теория
- `Runnable.run()` ничего не возвращает и не может бросить checked exception.
- `Callable<T>.call()` возвращает результат `T` и объявляет `throws Exception`.
- `ExecutorService.submit()` принимает и `Runnable`, и `Callable`. Для `Runnable` результат `Future<?>` равен `null`, для `Callable` — нужное значение.
- `Future.get(timeout, unit)` ждёт результат ограниченное время. `TimeoutException` означает, что вычисление ещё не готово; `ExecutionException` означает, что само вычисление упало, а причина лежит в `getCause()`.
- После `TimeoutException` нельзя просто позвонить `get()` второй раз без нового бюджета времени: это снова может заблокировать поток. Нужно либо отменить задачу, либо выделить новое ожидание осознанно.
- `cancel(true)` — запрос на прерывание. Задача сама решает, когда остановиться. Это не принудительное убийство потока: JVM не выдёргивает поток из произвольной точки.
- Корректная задача ловит `InterruptedException` и в `finally` делает обязательную уборку. Если исключение нельзя пробросить (например, внутри `Runnable`), восстанавливают флаг через `Thread.currentThread().interrupt()`; если можно — восстанавливают флаг и пробрасывают исключение дальше.

### Что сделано
- `CallableFutureDemo` отправляет три задачи: `Runnable`, `Callable` с суммой и `Callable` с `IOException`.
- Для долгой задачи используется `InterruptibleSum`: она считает с паузами, реагирует на прерывание и в `finally` выставляет флаг `closed` — это простая модель закрытия ресурса.
- Пул завершается через `shutdown` и `awaitTermination` в `finally`.

### Вывод демо
```text
Runnable: результат не возвращается
Future от Runnable: null
Future от Callable: 5050
Ошибка вычисления: IOException: проверенное исключение
Timeout: результат не получен за 50 мс
Отмена задачи: true
Задача завершилась: true
Ресурс закрыт после отмены: true
```

Точное число потерянного времени и момент timeout зависят от машины, но структура результата стабильна.

### Что могут спросить
**Чем `Callable` отличается от `Runnable`?** `Callable` возвращает значение и может бросить checked exception; `Runnable` — нет.

**Где искать причину ошибки?** В `ExecutionException.getCause()`, например `IOException`.

**Почему после timeout не ждут второй раз?** Потому что первое время уже истекло; повторное `get()` без нового бюджета снова может заблокироваться.

**Что делает `cancel(true)`?** Устанавливает флаг прерывания потока, если задача ещё выполняется. Задача должна сама обработать его.

## Задание 2. Последовательное преобразование

### Теория
- `CompletableFuture.supplyAsync(...)` создаёт стадию с результатом и запускает её в указанном executor.
- `thenApply` преобразует результат предыдущей стадии: `T → R`.
- `thenAccept` завершает цепочку и ничего не возвращает наружу: `T → void`.
- Если стадия уже завершилась к моменту добавления следующей, не-async стадия может выполниться в потоке вызывающего кода. В демо загрузка искусственно занимает 10 мс, поэтому все стадии выполняются в потоках `course-io-*`.
- `thenApply` для асинхронной функции даёт вложенный `CompletableFuture<CompletableFuture<T>>`.
- `thenCompose` «сплющивает» такой результат и даёт `CompletableFuture<T>`.

### Что сделано
- `buildCard`: `supplyAsync` загружает курс, `thenApply` форматирует карточку, `thenAccept` передаёт результат в `Consumer`.
- Все стадии используют один `ExecutorService` с именами потоков `course-io-*`.
- `loadUserEnrollments`: сначала загружается пользователь, затем `thenCompose` асинхронно загружает его записи.

### Вывод демо
```text
Карточка: JAVA-1 | Основы Java | 32h
Потоки: load=course-io-1, format=course-io-1, accept=course-io-1
Записи пользователя: [Enrollment[userId=101, courseCode=JAVA-1, completed=true], Enrollment[userId=101, courseCode=SQL-1, completed=false]]
```

### Что могут спросить
**Какой executor используется?** `Executors.newFixedThreadPool(3, ...)` с префиксом `course-io`.

**Почему не `thenApply` для загрузки записей?** Он вернул бы future внутри future. Нужен `thenCompose`, чтобы получить плоский `CompletableFuture<List<Enrollment>>`.

**Чем `thenApply` отличается от `thenAccept`?** `thenApply` возвращает новый результат, `thenAccept` только потребляет результат.

## Задание 3. `allOf` с сохранением результатов

### Теория
- `CompletableFuture.allOf` ждёт завершения всех futuroв, но сам возвращает `CompletableFuture<Void>`.
- Чтобы сохранить результаты, нужно держать список самих `CompletableFuture<T>` и после `allOf` собрать `join()` в исходном порядке списка ID.
- Тип результата сохраняется: `List<CompletableFuture<String>>` даёт `List<String>`.
- Политика fail-fast: если любая загрузка упала, общий результат считается ошибочным.
- Политика частичного результата: ошибки превращаются в обычные значения-результаты, затем разделяются на успешные данные и список ошибок.

### Что сделано
- `loadAllOrFail`: ждёт `allOf`, затем `join()` в порядке входных ID; при ошибке выбрасывается `CompletionException`.
- `loadWithErrors`: каждый future возвращает простой `Outcome` — либо значение, либо текст ошибки. Итог — `CourseBatchResult(values, errors)`.
- Обе политики сохраняют порядок `List.of(1, 99, 3)`.

### Вывод демо
```text
Fail-fast, всё загружено: [JAVA-1, WEB-1, SQL-1]
Fail-fast, ошибка: курс не найден
Частичный результат: [JAVA-1, SQL-1], ошибки: [Курс 99: курс не найден]
```

### Что могут спросить
**Почему порядок сохраняется?** Потому что `join()` вызывается по списку future в том же порядке, что и входные ID.

**Теряется ли типизация?** Нет: данные остаются `String`, ошибки — отдельный `List<String>`.

**В чём разница политик?** Fail-fast не отдаёт частичные данные; частичная политика отдаёт всё успешное и перечень ошибок.

## Задание 4. Правильный executor

### Теория
- CPU-bound задачи почти всё время считают. Для них разумно примерно `Runtime.getRuntime().availableProcessors()` потоков: больше ядер не ускорит счёт.
- Blocking I/O задачи большую часть времени ждут. Для platform threads нужен пул больше числа ядер, иначе потоки простаивают.
- Если выполнять и счёт, и ожидание в одном однопоточном executor, blocking-задача занимает единственный поток — это starvation.
- Virtual threads предназначены для большого числа ожидающих задач. Поток виртуальный дешёвый, но CPU всё равно ограничен числом ядер.

### Что сделано
- `starvation-*`: один поток сначала выполняет блокирующую задачу 200 мс, поэтому CPU-задача ждёт.
- `cpu-*`: пул размером с число доступных процессоров, только счёт.
- `io-*`: отдельный пул из 8 потоков для platform blocking I/O.
- `newVirtualThreadPerTaskExecutor()`: отдельный executor, где на каждую blocking-задачу создаётся виртуальный поток.

### Вывод демо
```text
Starvation: CPU-1499994, CPU ждал ~203 мс
CPU-результат: 5999995
Поток I/O: io-1
Virtual I/O задач выполнено: 20
```

### Что могут спросить
**Что такое starvation?** Ситуация, когда задача не получает ресурс, потому что единственный поток занят другой долгой задачей.

**Почему virtual threads не ускоряют CPU?** Потому что вычисления всё равно выполняются на процессорных ядрах. Виртуальные потоки помогают масштабировать ожидание, а не счёт.

**Почему block и CPU разделены?** Чтобы ожидание I/O не отбирало потоки у вычислений.

## Задание 5. Platform и virtual threads

### Теория
- Это учебное наблюдение, не полноценный benchmark: нет прогрева, усреднения по многим запускам и точного профилирования.
- Обе группы решают одно и то же число задач с одинаковым временем ожидания.
- Для модели ожидания используется `LockSupport.parkNanos`, а не `Thread.sleep` как модель CPU-работы. CPU-работа в демо есть в задании 4 и представляет собой обычный цикл.
- Наблюдаемые величины: время, число созданных именованных platform-потоков и примерное изменение памяти через `Runtime`.

### Что сделано
- `runPlatform(400, 32, 20 мс)` — 400 блокирующих задач в пуле из 32 platform-потоков.
- `runVirtual(400, 20 мс)` — те же 400 задач в `newVirtualThreadPerTaskExecutor()`.
- В virtual-варианте наших именованных platform-потоков `platform-exp-*` нет: виртуальные потоки работают поверх carrier-потоков JVM.

### Вывод демо
```text

Virtual:  ExperimentResult[mode=virtual, tasks=400, elapsedMs=26, namedPlatformThreads=0, memoryDeltaMb=1]
Это учебное наблюдение, не полноценный benchmark.
```

Цифры времени и памяти различаются между запусками; важно соотношение и объяснение.

### Что могут спросить
**Что здесь измерялось?** Время завершения, число наших platform-потоков и примерный расход памяти.

**Почему это не benchmark?** Потому что один прогон, нет прогрева и статистики.

**Почему virtual быстрее в этом примере?** Потому что все ожидания идут параллельно, а не очередь в 32 потока.

## Задание 6. Общий deadline

### Теория
- Общий бюджет времени фиксируется одной точкой: `deadline = System.nanoTime() + budget`. `System.nanoTime()` — монотонные часы, подходящие для интервалов.
- Перед каждой стадией вычисляется остаток: `deadline - System.nanoTime()`.
- Если остаток истёк, новая работа не запускается, а текущая отменяется через `cancel(true)`.
- После отмены нужно дождаться фактического завершения задачи: `Future.get()` после `cancel` бросает `CancellationException` сразу, но не гарантирует, что код задачи уже вышел.
- Preview API не используется: достаточно `Future`, `System.nanoTime()` и `get(timeout)`.
- Structured concurrency связывает время жизни подзадач с одной областью видимости. При выходе из области он сам отменяет и дожидается всех задач; в обычных `Future` это приходится делать вручную.

### Что сделано
- `runWithDeadline` последовательно запускает две стадии с budgets 120 мс и 40 мс.
- Перед каждым `get` вызывается `remainingNanos`.
- При timeout или `ExecutionException` задача отменяется, происходит ожидание latch завершения, затем исключение пробрасывается дальше.

### Вывод демо
```text
Успех: первая + вторая
Timeout: Стадия не уложилась в общий бюджет
```

### Что могут спросить
**Почему `System.nanoTime()`, а не `System.currentTimeMillis()`?** `currentTimeMillis` может изменяться при синхронизации системного времени; `nanoTime` монотонен.

**Зачем отменять задачу при timeout?** Чтобы не тратить ресурсы на результат, который уже не нужен.

**Какую проблему решает structured concurrency?** Он делает группу задач одной единицей: срок жизни, отмена и ожидание завершения управляются автоматически.
