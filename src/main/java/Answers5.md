# Задание по Java 5 - разборы задач

## Задание 1. Files.readString/writeString

### Теория
- В Java 11 появились методы `Files.writeString(path, text)` и `Files.readString(path)`. Они по умолчанию используют кодировку UTF-8.
- При работе с файлами могут возникать ошибки: файл не существует, по пути находится директория, нет прав на запись.
- Условие требует не ловить ошибку только ради печати и продолжения с ложным успехом. Это значит, что если операция не удалась, мы должны честно сообщить об этом, а не возвращать пустой результат.
- При чтении несуществующего файла выбрасывается `NoSuchFileException` (наследник `IOException`).
- При попытке прочитать директорию как файл выбрасывается `IOException`.

### Демонстрация
Вывод программы:
```
--- Задание 1: Files.readString/writeString ---
1. Запись в файл
Успешно записано в /mnt/d/vscode_work/DV_java/java-course/catalog.txt

2. Чтение из файла
Прочитано:
Курс 1: Java
Курс 2: Spring
Курс 3: Databases

3. Чтение несуществующего файла
Ожидаемая ошибка: NoSuchFileException

4. Чтение директории как файла
Ожидаемая ошибка: IOException
```
Объяснение вывода:
1. Строка успешно записалась в файл `catalog.txt` в кодировке UTF-8.
2. Файл успешно прочитался, и мы увидели его содержимое.
3. Попытка прочитать несуществующий файл привела к ожидаемой ошибке `NoSuchFileException`.
4. Попытка прочитать директорию как файл привела к ошибке `IOException`.

#### Правило
Для простого чтения и записи текста используйте `Files.readString` и `Files.writeString`. Всегда обрабатывайте `IOException`, чтобы программа не завершалась аварийно, но не скрывайте ошибки, если операция действительно не удалась.

# Задание 2. Reader/Writer

## Теория
- Файл на диске состоит из байтов (0 и 1). Чтобы прочитать из него текст, эти байты нужно превратить в символы (chars) с помощью кодировки (например, UTF-8).
- Классы `Reader` и `Writer` работают с символами, скрывая от нас работу с байтами.
- Чтение или запись по одному символу очень медленные. Для ускорения используются `BufferedReader` и `BufferedWriter`, которые читают/пишут данные целыми блоками (буфером).
- Метод `readLine()` читает строку целиком до перевода строки, а `newLine()` добавляет этот перевод при записи.
- Блок `try-with-resources` автоматически закрывает потоки (`reader` и `writer`) даже в случае ошибки.

### Демонстрация
Вывод программы:
```
--- Задание 2: Reader/Writer ---
Записано 3 строки.
Прочитано: Первая строка
Прочитано: Вторая строка
Прочитано: Третья строка

Всего строк: 3
Всего символов: 39
```
Объяснение вывода:
1. `BufferedWriter` записал три строки в файл, автоматически добавив символы перевода строки.
2. `BufferedReader` прочитал файл построчно, выводя каждую строку.
3. Счётчики посчитали 3 строки и 39 символов (без учёта символов перевода строки).

#### Правило
Для текстовых данных всегда используйте `BufferedReader` и `BufferedWriter`, оборачивая их в `try-with-resources` для автоматического закрытия. Это защищает от утечек памяти и работает быстрее посимвольного чтения.

# Задание 3. Try-with-resources

## Теория
- Конструкция `try-with-resources` позволяет автоматически закрывать ресурсы (файлы, потоки), которые реализуют интерфейс `AutoCloseable`. Блок `finally` с вызовом `.close()` больше не нужен.
- Если в одном `try` объявлено несколько ресурсов, они закрываются в **обратном порядке** (кто открыт последним, тот закрывается первым). Это нужно для безопасности: например, `BufferedWriter` оборачивает `FileWriter`, поэтому сначала закрывается буфер, а потом сам файл.
- Если исключение возникает внутри блока `try`, Java всё равно закрывает все ресурсы.
- Если при закрытии ресурса тоже возникает исключение, оно добавляется к основному как `suppressed` (подавленное), чтобы мы не потеряли информацию о первой ошибке.

### Демонстрация
Вывод программы:
```
--- Задание 3: Try-with-resources ---
Начинаем чтение и запись (с искусственным исключением)...
Поймано исключение: Искусственная ошибка посреди пайплайна!
Программа продолжает работу. Оба ресурса были закрыты.
```
Объяснение вывода:
1. Программа успешно открыла `BufferedReader` (для чтения) и `BufferedWriter` (для записи).
2. На второй строке было искусственно выброшено исключение `RuntimeException`.
3. Блок `try-with-resources` перехватил это и автоматически закрыл оба потока (сначала `writer`, затем `reader`).
4. Исключение было поймано в `catch`, программа не упала.

#### Правило
Всегда используйте `try-with-resources` для работы с любыми ресурсами, требующими закрытия. Это гарантирует отсутствие утечек памяти и файловых дескрипторов даже при возникновении исключений.

# Задание 4. Ленивые строки

## Теория
- Метод `Files.lines(path)` не читает файл сразу. Он возвращает ленивый `Stream<String>`, который читает строки по мере необходимости (например, при вызове `count()` или `forEach`). Это позволяет обрабатывать очень большие файлы, не загружая их целиком в память.
- Так как `Stream` держит файл открытым, тот, кто его создал, обязан его закрыть. Иначе произойдет утечка файловых дескрипторов.
- Правильный способ работы с `Files.lines` — использовать `try-with-resources`. Это гарантирует, что поток (и файл) будет закрыт автоматически.
- Ошибочный способ — вернуть `Stream` из метода наружу. Вызывающий код может забыть его закрыть, и компилятор об этом не предупредит.

### Демонстрация
Вывод программы:
```
--- Задание 4: Ленивые строки ---
Правильный вариант (внутри try-with-resources):
Найдено строк: 3

Ошибочный вариант (возврат наружу):
Поток получен. Но кто его закроет?
Поток закрыт вручную.
```
Объяснение вывода:
1. В правильном варианте `Stream` находится внутри `try-with-resources`, поэтому после подсчета строк (3) он автоматически закрылся.
2. В ошибочном варианте метод `getLeakedStream` вернул поток наружу. Вызывающий код (метод `run`) был вынужден вручную вызвать `.close()`, чтобы предотвратить утечку.

#### Правило
Никогда не возвращайте `Stream` (или `Reader`/`Writer`) из метода, если не уверены, что вызывающий код закроет его. Используйте `try-with-resources` там, где ресурс создается, или возвращайте уже собранные данные (например, `List<String>`), а не сам поток.

# Задание 5. Бинарный формат

## Теория
- Бинарные файлы хранят данные в виде байтов, а не символов. Они компактнее и быстрее для программ, но нечитаемы для человека.
- `DataOutputStream` и `DataInputStream` позволяют записывать и читать примитивы Java (`int`, `double`, `boolean`) в бинарном виде.
- **Magic header** — специальное число в начале файла (у нас `0xCAFE`). Оно нужно, чтобы программа убедилась, что перед ней её файл, а не случайный мусор.
- **Version** — номер версии формата. Если программа видит незнакомую версию, она должна отказаться читать файл.
- Если файл поврежден или недописан, при чтении возникает `EOFException` (End of File). Это нужно обрабатывать.

### Демонстрация
Вывод программы:
```
--- Задание 5: Бинарный формат ---
Файл успешно записан: catalog_dir/binary_data.bin

Чтение файла:
Найдено записей: 3
 - Java Course: 199.99
 - Spring Course: 299.99
 - SQL Course: 149.99
```
Объяснение вывода:
1. `DataOutputStream` записал magic header (0xCAFE), версию (1), количество записей (3) и сами записи (название + цена).
2. При чтении `DataInputStream` сначала проверил magic header и версию. Если бы они не совпали, программа выдала бы ошибку.
3. Счётчик записей (3) позволил циклу прочитать ровно 3 пары «название-цена».

#### Правило
Для бинарных форматов всегда используйте magic header и версию, чтобы защититься от чтения чужих или поврежденных файлов. Всегда обрабатывайте `EOFException` при чтении.
