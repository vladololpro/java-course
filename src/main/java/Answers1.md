# Задача 1. Один контракт, две реализации

## Что сделано
- Интерфейс `CourseFormatter` с методом `format(Course)`.
- Реализации `CompactCourseFormatter` и `DetailedCourseFormatter`.
- Демонстрация в `Main`: одна переменная интерфейсного типа, две реализации.

## Что известно компилятору
- Компилятор видит только статический тип переменной - `CourseFormatter`. Он проверяет, что метод `format(Course)` объявлен в этом типе, и что типы аргумента и возвращаемого значения совпадают.
- Что лежит внутри переменной - `CompactCourseFormatter` или `DetailedCourseFormatter` - компилятор не анализирует. Оба класса реализуют интерфейс, значит, оба умеют `format`.

## Эксперимент
- Если убрать метод `format` из `CourseFormatter`, компилятор выдаёт четыре ошибки:


- Хотя в `CompactCourseFormatter` и `DetailedCourseFormatter` методы `format` остались - компилятор их не видит, потому что смотрит на тип переменной (`CourseFormatter`), а не на её содержимое.

## Что выбирается во время выполнения
- JVM во время выполнения смотрит на динамический тип объекта - фактический класс, лежащий в переменной, - и вызывает его реализацию метода `format`. Поэтому один и тот же вызов `formatter.format(course)` даёт разный результат в зависимости от того, какой объект сейчас в переменной.

# Задача 2. Dynamic dispatch на бумаге

## Что сделано
- Иерархия `NotificationSender` -> `EmailSender`, `ConsoleSender`.
- Метод `send(String)` переопределён в наследниках (override).
- Метод `send(String, int)` добавлен в родителя как перегруженный (overload).
- `Main` вызывает методы через переменные разных статических типов.

## Override: выбор по динамическому типу
- Метод `send(String)` есть у родителя и переопределён у наследников. Компилятор проверяет только, что метод объявлен в статическом типе переменной. Какую реализацию вызвать - решает JVM по фактическому классу объекта.

- Пример:
  - `NotificationSender asBase = new EmailSender();`.
  - `asBase.send("hello");` → `EmailSender.send: hello`.
  - Статический тип - `NotificationSender`, но объект - `EmailSender`, поэтому вызывается его реализация.

## Overload: выбор по статическому типу
- Метод `send(String, int)` объявлен только в `NotificationSender`. `EmailSender` его не переопределял (переопределил только `send(String)`).
- Компилятор ищет подходящий метод по статическому типу переменной и типам аргументов.   Находит `NotificationSender.send(String, int)` и связывает вызов с ним.

- Пример:
  - `NotificationSender asBase = new EmailSender();`
  - `asBase.send("hello", 5);` → `NotificationSender.send(priority=5): hello`
  - Хотя объект - `EmailSender`, у него нет собственной версии `send(String, int)`, поэтому вызывается родительская.

# Задача 3. Полиморфный массив

## Что сделано
- Массив интерфейсного типа `CourseFormatter[]` с тремя реализациями.
- Обход через `for-each` без `if` по типу.
- Добавлена третья реализация `JsonCourseFormatter`, интерфейс и первые две реализации переиспользованы из `task01`.
- Обход не изменился при добавлении третьей реализации.

## Почему это полиморфный массив
- Массив объявлен как `CourseFormatter[]` - то есть массив интерфейсного типа. В него можно положить объект любого класса, реализующего `CourseFormatter`.
- При обходе переменная `formatter` имеет тип `CourseFormatter`. На каждом вызове `formatter.format(course)` JVM смотрит на динамический тип объекта (фактический класс) и вызывает его реализацию. Поэтому один и тот же код обхода работает по-разному для разных элементов массива.

## Почему нет `if` по типу
- Логика «что делать» инкапсулирована в самих классах-реализациях через метод `format`. Клиенту не нужно проверять, кто именно в массиве: он просто вызывает метод контракта. Это и есть «клиент зависит только от интерфейса».

## Добавление четвёртой реализации
- Если появится новая реализация (например, `MisterusCourseFormatter`):
1. Создаётся новый класс, реализующий `CourseFormatter`.
2. Он добавляется в массив в `Main`.
3. Код обхода НЕ меняется.
- Это главный критерий задачки: расширение не затрагивает клиентский код.

# Задача 4. Абстрактный базовый класс

## Что сделано
- Абстрактный класс `AbstractNotificationSender` с полем `recipient`.
- Публичный метод `send(String)` - общий алгоритм, помечен `final`.
- Абстрактный метод `doSend(String)` - точка расширения.
- Наследники `EmailSender`, `ConsoleSender` реализуют `doSend`.
- `Main` демонстрирует три случая: email, console, пустой адресат.

## Что общего в алгоритме
- Метод `send(String)` описывает одинаковую последовательность для всех наследников:
1. Проверить адресата.
2. Напечатать начало отправки.
3. Вызвать `doSend` — специфичную реализацию наследника.
4. Напечатать завершение.
- Шаги 1, 2, 4 не зависят от типа отправителя - они в родителе. Шаг 3 разный - он вынесен в абстрактный `doSend`.

## Почему `send` сделан `final`
- `final` запрещает переопределение. Это значит, что наследник не может изменить общий алгоритм: не может, например, пропустить проверку адресата или изменить порядок шагов. Инвариант поведения защищён.
- Если бы `send` не был `final`, наследник мог бы его переопределить и сломать контракт родителя - например, отправлять пустому адресату. `final` это запрещает на уровне компилятора.

## Что даёт абстрактный класс
- Общий код (проверка адресата, обрамление) не дублируется.
- Каждый наследник обязан реализовать `doSend` - компилятор это проверяет.
- Создать `new AbstractNotificationSender(...)` нельзя - этот класс только для наследования.

# Задача 5. Интерфейс или абстрактный класс

## 1. Identifiable
- Решение: interface.
- Мотивировка: контракт «умею возвращать идентификатор». Общего состояния нет, id хранится в каждом классе своё. Много несвязанных классов могут быть Identifiable: Course, Student, EnrollmentRequest. Иерархия классов тут не нужна.
- Цена изменения: если сделать абстрактным классом, наследники потеряют возможность наследовать другой класс (в Java одно наследование классов). Если убрать вовсе - код, работающий с «чем угодно с id», придётся дублировать.
- Пример:
```java
public interface Identifiable {
    long id();
}
```

## 2. CoursePolicy
- Решение: interface.
- Мотивировка: поведение-стратегия. У политики нет состояния, есть только метод «можно ли допустить». Реализаций несколько (по возрасту, вместимости) - они не связаны иерархией.
- Цена изменения: абстрактный класс - лишнее ограничение, нет общего состояния. Обычный класс - клиент завяжется на конкретную политику, потеряется подменяемость. Без типа - придётся писать if по строковому типу политики.
- Пример:
```java
public interface CoursePolicy {
    boolean canEnroll(Student student, Course course);
}
```

## 3. BaseEntity
- Решение: abstract class.
- Мотивировка: есть общее состояние и общий код. Иерархия осмысленна: Course, Student, Enrollment - все являются BaseEntity. Java позволяет только одно наследование классов — BaseEntity хороший кандидат.
- Цена изменения: интерфейс - потеряется общее состояние, поля придётся дублировать в каждом классе. Обычный класс - можно случайно создать new BaseEntity(), что бессмысленно.
- Пример:
```java
public abstract class BaseEntity {
    protected long id;
    protected Instant createdAt;

    public long id() { return id; }
    public Instant createdAt() { return createdAt; }
}
```

## 4. Formatter
- Решение: interface.
- Мотивировка: контракт «преобразовать объект в строку». Форматы разные (компакт, подробно, JSON, XML) - не связаны иерархией. Общего состояния нет.
- Цена изменения: абстрактный класс - избыточное ограничение. Обычный класс - теряется полиморфизм. Без типа - форматтеры станут разрозненными методами, клиент потеряет единый контракт.
- Пример:
```java
public interface Formatter<T> {
    String format(T value);
}
```

## 5. ClockProvider
- Решение: interface.
- Мотивировка: контракт «верни текущий момент». Реализаций минимум две: реальное время и фиксированное. Общего состояния нет. Интерфейс позволяет подменять источник времени без изменения кода. Java уже имеет похожий интерфейс - java.time.Clock.
- Цена изменения: абстрактный класс - не нужен, нет общего состояния. Обычный класс - нельзя подменить в тестах. Без типа - придётся везде вызывать Instant.now(), код станет недетерминированным.
- Пример:
```java
public interface ClockProvider {
    Instant now();
}
```

# Задача 6. Переопределение без случайной перегрузки

## Что сделано
- Класс `BrokenSender` с методом `send(String)`.
- Класс `BrokenEmailSender`, в котором `send(Object)` - это перегрузка, а не override. Без `@Override` компилятор молчит.
- Класс `FixedSender` и `FixedEmailSender` с корректным override и `@Override`.
- `Main` демонстрирует разницу: сломанный случай даёт родительскую реализацию, исправленный - наследника.

## Ловушка без `@Override`
- Код в `BrokenEmailSender` компилируется без ошибок:
```java
BrokenSender broken = new BrokenEmailSender();
broken.send("hello");   // → base.send: hello, а не broken.send(Object)
```
- Компилятор видит `send(String)` в статическом типе переменной (`BrokenSender`). JVM ищет `send(String)` в динамическом типе (`BrokenEmailSender`), не находит (там только `send(Object)`), поднимается в родителя и вызывает его реализацию.
- Программист мог думать, что переопределил `send`, но фактически добавил перегруженный метод. С `@Override` компилятор поймал бы это сразу.

## Правило
- Везде, где ожидается переопределение - ставь `@Override`. Это бесплатная проверка компилятора: если метод не переопределяет родительский, компиляция упадёт.

# Задача 7. Композиция вместо наследования

## Что сделано
- Интерфейс `NotificationSender` как общий контракт.
- Реальные реализации: `EmailSender`, `ConsoleSender`.
- Декораторы: `LoggingSender`, `RetrySender`, `MetricsSender`. Каждый содержит внутри другой `NotificationSender` и делегирует ему вызов, добавляя своё поведение.
- `Main` показывает два порядка композиции и разницу поведения.

## Почему композиция, а не наследование
- Наследование дало бы взрыв комбинаций: под каждый аспект и его порядок - отдельный подкласс (`LoggingEmailSender`, `RetryLoggingEmailSender`, `MetricsRetryLoggingEmailSender` и т.д.). Это уже 2^n классов на n аспектов.
- Декораторы дают n классов вместо 2^n: каждый аспект - один класс, комбинации - через вложение в коде сборки.

## Как работает декоратор
- Декоратор реализует тот же интерфейс, что и оборачиваемый объект, и содержит его внутри. В своём методе `send` он:
1. Делает что-то до (например, логирует).
2. Делегирует вызов `inner.send(...)`.
3. Делает что-то после.
- Клиент видит один `NotificationSender` и не знает, что внутри цепочка.

## Два порядка композиции
- Порядок 1: `Logging(Retry(Email))`.
```
LOG before: hello
RETRY attempt 1/2
  [EMAIL] hello
RETRY attempt 2/2
  [EMAIL] hello
LOG after: hello
```
- Логирование снаружи - видит retry как одно событие. Пара LOG один раз.

- Порядок 2: `Retry(Logging(Email))`.
```
RETRY attempt 1/2
LOG before: hello
  [EMAIL] hello
LOG after: hello
RETRY attempt 2/2
LOG before: hello
  [EMAIL] hello
LOG after: hello
```
- Логирование внутри - вызывается на каждой попытке. Пара LOG дважды.

# Задача 8. Нарушение LSP

## Что было бы неправильно
- Стандартная «сломанная» иерархия:
```java
class CourseRepository {
    void save(Course c) { ... }
    Optional<Course> findById(long id) { ... }
}

class ReadOnlyCourseRepository extends CourseRepository {
    @Override
    void save(Course c) {
        throw new UnsupportedOperationException();
    }
}
```
- Проблема: клиент, работающий с `CourseRepository`, ожидает, что `save` сохраняет. Если ему подсунут `ReadOnlyCourseRepository`, метод упадёт в runtime. Клиент не мог этого предвидеть - статический тип обещал работающий `save`.
- Это нарушение принципа подстановки Лисков (LSP): объект наследника должен быть подставляем вместо объекта родителя без сюрпризов.

## Что сделано
- Интерфейсы разделены по возможностям:
  - `ReadableCourseRepository` - только `findById`.
  - `WritableCourseRepository` - только `save`.
  - `FullCourseRepository` - оба.
  - `ReadOnlyCourseRepository` - реализует только `ReadableCourseRepository`.
  - `InMemoryCourseRepository` - реализует `FullCourseRepository`.
- `ReadOnlyCourseRepository` больше НЕ обещает `save`. Нарушение LSP исчезло: read-only реализация не может попасть туда, где нужен `save`.

## Как это работает в `Main`
- Клиент чтения (`printCourse`) принимает `ReadableCourseRepository`. Работает и с read-only, и с полным.
- Клиент записи (`addCourse`) принимает `WritableCourseRepository`. Полный репозиторий подходит, read-only - нет.
- Попытка передать read-only в клиент записи ловится компилятором:
```
error: incompatible types: ReadOnlyCourseRepository cannot be converted to WritableCourseRepository
```
- Это ошибка компиляции, а не исключение в runtime. Ошибка видна сразу, до запуска.

## Использованные средства стандартной библиотеки
- `Map<Long, Course>` - словарь «ключ -> значение». В нашем случае ключ - id курса, значение - сам объект Course. Позволяет быстро найти курс по id: `storage.get(id)`. Если ключа нет - вернётся null.

- `HashMap` - стандартная реализация `Map` на хеш-таблице. Поиск по ключу почти мгновенный (в среднем O(1)), не зависит от размера словаря. Переменная объявлена как `Map`, а создаётся как `HashMap`: тип переменной - абстракция, реализация - конкретность.

- `Optional<Course>` - контейнер, который может содержать значение, а может быть пустым. Используется в `findById`, чтобы честно показать: «курс может не найтись». Клиент обязан обработать случай «не найдено» - компилятор это проверит. Это лучше, чем возвращать null: null не виден из сигнатуры, легко забыть проверить и получить NullPointerException.
