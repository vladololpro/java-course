## Задание 1. `Callable` и `Future`

### Условие
Показать разницу между `Runnable` и `Callable`, получить результат через `Future`, ограничить ожидание timeout, отделить timeout от ошибки вычисления, отменить долгую задачу через `cancel(true)` и корректно обработать прерывание.

### Теория
- `Runnable.run()` ничего не возвращает и не объявляет checked exception.
- `Callable<T>.call()` возвращает `T` и может бросить `Exception`.
- `ExecutorService.submit` принимает оба типа. Для `Runnable` результат `Future` равен `null`, для `Callable` — возвращённое значение.
- `Future.get(timeout, unit)` ждёт результат не дольше заданного времени.
- `TimeoutException` — задача ещё не успела завершиться. `ExecutionException` — задача завершилась с ошибкой, причина лежит в `getCause()`.
- После timeout нельзя просто вызвать `get()` второй раз без нового бюджета времени: можно снова заблокироваться.
- `cancel(true)` — запрос на прерывание, а не принудительное убийство потока. Задача сама решает, когда остановиться.
- При `InterruptedException` нужно восстановить флаг через `Thread.currentThread().interrupt()` и сделать обязательную уборку в `finally`.

### Объяснение кода
- `ExecutorSupport.named("future")` задаёт понятные имена потоков, а `shutdownAndAwait` завершает пул в `finally`.
- В `CallableFutureDemo.demo()` отправляются три задачи:
  - `Runnable` просто печатает сообщение, его `Future` равен `null`;
  - `Callable` считает сумму `1..100` и возвращает `5050`;
  - `Callable` бросает `IOException`, и ошибка достаётся из `ExecutionException.getCause()`.
- Для долгой задачи используется `InterruptibleSum`: цикл со сном на 1 мс, timeout 50 мс, затем `cancel(true)`.
- `InterruptibleSum` не создаёт отдельный класс `Resource`. Вместо этого в `finally` выставляется простое поле `closed` — это учебная модель закрытия ресурса.
- `CountDownLatch finished` позволяет дождаться фактического выхода задачи после отмены: `Future.get()` после `cancel` может вернуться раньше, чем поток реально закончит код.

**Подробнее по шагам.**
1. Создаётся пул из двух потоков с именами `future-1`, `future-2`.
2. Отправляется `Runnable`; `get` возвращает `null`.
3. Отправляется `Callable`; `get` возвращает `5050`.
4. Отправляется `Callable` с `IOException`; ловится `ExecutionException`, печатается причина.
5. Создаётся `InterruptibleSum(1_000_000)` и отправляется в пул.
6. `get(50, MILLISECONDS)` бросает `TimeoutException`.
7. Вызывается `cancel(true)`, то есть потоку выставляется флаг прерывания.
8. `Thread.sleep(1)` внутри цикла реагирует на прерывание, задача восстанавливает флаг и выбрасывает `InterruptedException`.
9. В `finally` выставляется `closed = true` и открывается защёлка `finished`.
10. `awaitFinished(1, SECONDS)` подтверждает, что задача реально завершилась.
11. В `finally` пул завершается через `shutdown`, а при необходимости `shutdownNow`.

**Почему timeout и ошибка — разные вещи.** При timeout результат ещё может появиться позже. При `ExecutionException` вычисление уже закончилось неудачно, и нужно смотреть причину.

**Почему не вызываем `get()` повторно.** Первое ожидание уже истекло. Повторное `get()` без нового бюджета снова может ждать неопределённо долго.

**Что делает прерывание.** Оно только просит задачу остановиться. Код задачи должен проверять или ловить прерывание и корректно завершаться.

```text
Отмена задачи: true

Ресурс закрыт после отмены: true
```

### Что могут спросить и как отвечать
**Чем `Callable` отличается от `Runnable`?** `Callable` возвращает результат и может бросить checked exception; `Runnable` — нет.

**Что вернёт `Future` от `Runnable`?** `null`.

**Где искать причину ошибки?** В `ExecutionException.getCause()`, здесь это `IOException`.

**Чем `TimeoutException` отличается от `ExecutionException`?** Timeout — задача не успела за отведённое время. `ExecutionException` — задача уже упала с ошибкой.

**Можно ли после timeout просто позвонить `get()` ещё раз?** Нельзя без нового осознанного бюджета времени: снова возможна блокировка.

**Что делает `cancel(true)`?** Устанавливает флаг прерывания. Это запрос, а не гарантированное мгновенное убийство.

**Зачем восстанавливать флаг прерывания?** Чтобы вышестоящий код тоже увидел, что поток был прерван.

**Зачем `CountDownLatch finished`?** Чтобы дождаться реального завершения задачи после отмены.

**Почему в `finally` выставляется `closed`?** Потому что уборка должна выполниться и при успехе, и при ошибке, и при отмене.

**Как завершается пул?** `shutdown()` запрещает новые задачи, `awaitTermination` ждёт завершения; если время вышло, вызывается `shutdownNow()`.

## Задание 2. Последовательное преобразование

### Условие
Построить цепочку `supplyAsync → thenApply → thenAccept`, зафиксировать потоки и executor, показать разницу между `thenApply` и `thenCompose` на примере загрузки записей пользователя.

### Теория
- `supplyAsync` создаёт `CompletableFuture<T>` и запускает поставщика в executor.
- `thenApply` преобразует результат: `T → R`.
- `thenAccept` потребляет результат и ничего не возвращает: `T → void`.
- Если указан один и тот же executor, все стадии выполняются в его потоках.
- `thenApply` с асинхронной функцией даёт `CompletableFuture<CompletableFuture<T>>`.
- `thenCompose` «сплющивает» вложенный future и даёт плоский `CompletableFuture<T>`.

### Объяснение кода
- Данные курсов, пользователей и записей хранятся в `Map.of` — это обычные тестовые заглушки.
- `buildCard`:
  - `supplyAsync` загружает курс и запоминает имя потока в `LoadedCourse`;
  - `thenApply` собирает строку карточки и запоминает поток форматирования;
  - `thenAccept` передаёт итог в `Consumer<CardTrace>` и запоминает поток печати.
- `CardTrace` содержит карточку и три имени потоков. Это нужно, чтобы наглядно показать, где выполнялись стадии.
- `loadUserEnrollments` сначала загружает пользователя, затем через `thenCompose` асинхронно загружает его записи.
- `demo` создаёт `Executors.newFixedThreadPool(3, ...)` с префиксом `course-io` и обязательно закрывает его в `finally`.
- Имитация I/O сделана через `LockSupport.parkNanos`, чтобы поток действительно ожидал, но не спал как модель CPU-работы.

**Подробнее по шагам.**
1. Создаётся пул `course-io` на 3 потока.
2. `buildCard` отправляет загрузку курса в пул.
3. Загрузка занимает 10 мс и возвращает `Course` вместе с именем потока.
4. `thenApply` форматирует карточку и фиксирует следующий поток.
5. `thenAccept` отдаёт карточку в `sink`, где фиксируется третий поток.
6. Основной поток ждёт `get(3, SECONDS)` и печатает карточку и потоки.
7. `loadUserEnrollments` загружает пользователя.
8. `thenCompose` запускает вторую асинхронную загрузку записей.
9. Итог — плоский `CompletableFuture<List<Enrollment>>`.

**Почему все стадии в `course-io-*`.** Загрузка занимает 10 мс, поэтому когда добавляются следующие стадии, предыдущая уже выполняется в пуле. Если бы результат был готов сразу, не-async стадия могла бы выполниться в потоке вызывающего кода.

**Почему `thenCompose`, а не `thenApply`.** `loadEnrollments` сама возвращает `CompletableFuture`. `thenApply` оставил бы future внутри future.


Имена потоков могут отличаться, но префикс `course-io` сохраняется.

### Что могут спросить и как отвечать
**Какой executor используется?** `newFixedThreadPool(3)` с именами `course-io-*`.

**Что делает `supplyAsync`?** Асинхронно вычисляет значение и возвращает `CompletableFuture` с результатом.

**Чем `thenApply` отличается от `thenAccept`?** `thenApply` возвращает новый результат, `thenAccept` только потребляет.

**Почему цепочка не блокирует основной поток?** Потому что каждая стадия выполняется в executor, а основной поток только ждёт результат через `get`.

**Что будет, если курс не найден?** `CompletableFuture` завершится исключительно; при `get` получим `ExecutionException`.

**Зачем `CardTrace`?** Чтобы показать и результат, и потоки всех трёх стадий.

**Что такое плоский future?** `CompletableFuture<List<Enrollment>>`, а не `CompletableFuture<CompletableFuture<List<Enrollment>>>`.

**Как получить плоский future?** Через `thenCompose`.

**Можно ли обойтись без executor?** Можно, тогда стадии выполнялись бы в `ForkJoinPool.commonPool()`, и имена потоков были бы другими.

**Зачем shutdown в finally?** Чтобы не оставить потоки после демо или при падении.

## Задание 3. `allOf` с сохранением результатов

### Условие
Запустить несколько загрузок через `CompletableFuture`, дождаться всех через `allOf`, сохранить порядок и типы результатов, реализовать fail-fast и частичный результат с ошибками.

### Теория
- `CompletableFuture.allOf` ждёт завершения всех future, но возвращает `CompletableFuture<Void>`.
- Результаты нужно брать из исходного списка future.
- Если вызывать `join()` по списку в порядке входных ID, порядок результата сохраняется.
- Fail-fast: если хоть одна загрузка упала, весь результат считается ошибочным.
- Частичный результат: ошибки превращаются в обычные данные, затем разделяются на успешные значения и список ошибок.

### Объяснение кода
- `COURSES` — простой `Map<Long, String>` с тремя курсами.
- `load(id)` спит 5 мс через `parkNanos` и бросает `IllegalArgumentException`, если курс не найден.
- `loadAllOrFail`:
  - создаёт `List<CompletableFuture<String>>` в порядке входных ID;
  - ждёт `allOf`;
  - после этого собирает `join()` в том же порядке.
- `loadWithErrors` использует очень простой `record Outcome(String value, String error)`:
  - успех — `new Outcome(value, null)`;
  - ошибка — `new Outcome(null, текст)`.
- После `allOf` success-значения и ошибки раскладываются по двум спискам и упаковываются в `CourseBatchResult(values, errors)`.
- `List.copyOf` не позволяет изменять итоговые списки извне.

**Подробнее по шагам.**
1. Создаётся список future по списку ID.
2. Каждый future загружает свой курс в пуле.
3. `allOf` ждёт завершения всех загрузок.
4. В fail-fast варианте `join()` первого упавшего future выбрасывает `CompletionException`.
5. В демо это поймать как `ExecutionException`, и печатается причина `курс не найден`.
6. В варианте с ошибками каждая загрузка возвращает `Outcome`, а не выбрасывает исключение наружу.
7. Для `Outcome` с ошибкой заполняется `errors`, для остальных — `values`.
8. Порядок сохраняется, потому что перебор идёт по исходному списку future.

**Почему `allOf` не возвращает список.** Он нужен только как сигнал «все готовы». Данные остаются в исходных future.

**Почему порядок не зависит от скорости загрузок.** Потому что результат собирается по индексу в списке, а не по моменту завершения.

### Что могут спросить и как отвечать
**Что возвращает `allOf`?** `CompletableFuture<Void>`.

**Как сохранить результаты?** Держать список future и вызывать `join()` в исходном порядке.

**Как сохранить тип?** `List<CompletableFuture<String>>` даёт `List<String>`.

**Что такое fail-fast?** Ошибка любой части означает отказ всей операции.

**Что такое частичный результат?** Успешные данные возвращаются отдельно, ошибки — отдельно.

## Задание 4. Правильный executor

### Условие
Показать starvation при смешивании CPU- и blocking-задач, разделить executor’ы по типу работы, переписать blocking-задачи на virtual-thread-per-task executor и объяснить размеры и типы пулов.

### Теория
- CPU-bound задачи почти всё время считают. Для них ориентир — число доступных процессоров.
- Blocking I/O задачи большую часть времени ждут. Для platform threads пул обычно больше числа ядер.
- Starvation — ситуация, когда задача не получает поток, потому что он занят другой задачей.
- Virtual threads дешевле platform threads и подходят для множества ожидающих задач.
- Virtual threads не увеличивают число процессорных ядер, поэтому CPU-работу они не ускоряют.

### Объяснение кода
- `demonstrateStarvation` создаёт `newSingleThreadExecutor`.
- Сначала в него отправляется blocking-задача на 200 мс, затем CPU-задача.
- CPU-задача ждёт, пока освободится единственный поток; замер prints `~203 мс`.
- `demonstrateSeparateExecutors` создаёт:
  - `cpu` размером `availableProcessors()`;
  - `io` размером 8 для platform blocking I/O.
- `demonstrateVirtualThreads` использует `Executors.newVirtualThreadPerTaskExecutor()` в try-with-resources.
- Отправляется 20 задач, каждая ждёт 20 мс через `LockSupport.parkNanos`.
- `cpuWork` — обычный цикл без сна, то есть модель CPU-работы.
- `block` — модель ожидания I/O.

**Подробнее по шагам.**
1. В первом демо единственный поток занимается ожиданием 200 мс.
2. CPU-задача может стартовать только после освобождения потока.
3. Замер времени показывает задержку.
4. Во втором демо CPU и I/O используют разные пулы.
5. CPU-пул размером с число ядер: лишние потоки не добавят процессора.
6. I/O-пул на 8 потоков покрывает ожидание.
7. В третьем демо на каждую blocking-задачу создаётся виртуальный поток.
8. Executor закрывается автоматически через try-with-resources.

**Почему один пул на всё плохо.** Blocking-задача занимает поток, и CPU-задача его не получает.

**Почему virtual threads подходят для I/O.** Они дешёвые, поэтому можно создать много потоков для ожидания и не бояться большого расхода памяти.

**Почему virtual threads не заменяют CPU-пул.** CPU-работа всё равно выполняется на ядрах. Для счёта достаточно `availableProcessors()`.

### Что могут спросить и как отвечать
**Что такое starvation?** Задача ждёт ресурс, который занят другой задачей.

**Почему CPU-пул по числу ядер?** Лишние потоки только добавят переключения контекста.

**Почему I/O-пул больше?** Потоки часто простаивают в ожидании, поэтому нужно больше потоков, чтобы занять процессор.

**Что делает `newVirtualThreadPerTaskExecutor`?** Создаёт виртуальный поток на каждую задачу.

**Почему virtual threads не ускоряют счёт?** Счёт ограничен процессорными ядрами, а не числом потоков.

**Почему `parkNanos`, а не `Thread.sleep` как CPU?** `parkNanos` здесь модель ожидания. CPU в демо — отдельный цикл.

**Какой пул используется для starvation?** Один `newSingleThreadExecutor`.

**Как исправлена проблема?** Пулы CPU и I/O разделены, а blocking-задачи переведены на virtual threads.

**Зачем try-with-resources для virtual executor?** `newVirtualThreadPerTaskExecutor` реализует `AutoCloseable`, и закрытие гарантировано.

**Какой размер I/O-пула выбран?** 8 потоков как простой учебный ориентир.

## Задание 5. Platform и virtual threads

### Теория

## Задание 6. Общий deadline

### Условие
Написать две стадии с общим бюджетом времени. Перед каждой стадией вычислять остаток от монотонных часов, отменять ненужную работу и дожидаться её завершения. Не использовать preview API. Объяснить, какую проблему решает structured concurrency.

### Теория
- `System.nanoTime()` — монотонные часы, пригодные для измерения интервалов.
- Общий deadline фиксируется один раз: `deadline = now + budget`.
- Перед каждой стадией считается остаток: `deadline - now`.
- Если остаток истёк, новая стадия не запускается.
- `Future.get` после `cancel(true)` может сразу бросить `CancellationException`, поэтому отдельно нужен latch завершения задачи.
- Preview API в курсе не используется: достаточно `Future`, `System.nanoTime()` и `get(timeout)`.
- Structured concurrency связывает время жизни подзадач с одной областью: при выходе из области платформа сама отменяет и дожидается задач.

### Объяснение кода
- `runWithDeadline` создаёт один `deadline = System.nanoTime() + budget.toNanos()`.
- Первая стадия — `TimedTask("первая", 120 мс)`, вторая — `TimedTask("вторая", 40 мс)`.
- Метод `await` перед `future.get` вызывает `remainingNanos(deadline)`.
- Если время вышло, `remainingNanos` бросает `TimeoutException`.
- Если `get` сам вышел по timeout или упал с `ExecutionException`, задача отменяется и дожидается через `CountDownLatch`.
- `TimedTask` в `finally` выставляет `closed` и открывает защёлку `finished`.
- `demo` показывает успешный бюджет 250 мс и unsuccessful бюджет 80 мс.

**Подробнее по шагам.**
1. Фиксируется общий deadline.
2. Запускается первая задача на 120 мс.
3. Считается остаток; `get` ждёт не дольше остатка.
4. Запускается вторая задача на 40 мс.
5. Снова считается остаток от того же deadline.
6. При бюджете 250 мс обе стадии успевают: `первая + вторая`.
7. При бюджете 80 мс первая стадия не укладывается.
8. `await` отменяет задачу, ждёт latch и бросает `TimeoutException`.
9. Демо ловит исключение и печатает сообщение.

**Почему один deadline на две стадии.** Потому что пользователю важен общий срок, а не отдельные лимиты каждой стадии.

**Почему `nanoTime`, а не `currentTimeMillis`.** Системное время может измениться при синхронизации; `nanoTime` монотонен.

**Зачем дожидаться задачи после cancel.** `cancel(true)` только запрашивает остановку. Нужно убедиться, что код задачи действительно вышел и больше не держит ресурсы.

**Что решает structured concurrency.** В обычном `Future` отмену и ожидание группы задач пишем вручную. Structured concurrency делает группу задач одной единицей: срок жизни, ошибки и отмена управляются автоматически при выходе из области.

Фактический вывод `java8.Main` для задания 6:

```text
Успех: первая + вторая
Timeout: Стадия не уложилась в общий бюджет
```

### Что могут спросить и как отвечать
**Как считается остаток времени?** `deadline - System.nanoTime()`.

**Почему `System.nanoTime()`?** Он монотонный и подходит для интервалов.

**Что делает `remainingNanos`?** Проверяет, что бюджет не исчерпан, и возвращает остаток в наносекундах.

**Почему перед каждой стадией пересчитывается остаток?** Потому что предыдущая стадия могла съесть часть бюджета.

**Что происходит при timeout?** Задача отменяется, дожидается latch, и пробрасывается `TimeoutException`.

**Чем timeout отличается от ошибки задачи?** Timeout — время вышло, ошибка — задача упала сама.

**Зачем `cancel(true)`?** Чтобы задача получила прерывание и прекратила ненужную работу.

**Почему после cancel нужен latch?** `Future.get` после отмены не гарантирует, что код задачи уже завершился.

**Какой preview API не используется?** Structured concurrency остаётся только объяснённой идеей; в коде обычные `Future`.

**Какую проблему решает structured concurrency?** Автоматически связывает и отменяет все вложенные задачи при выходе из области видимости.

## Краткая шпаргалка

- `Runnable` не возвращает результат; `Callable<T>` возвращает `T`.
- `Future` от `Runnable` равен `null`; от `Callable` — результат.
- `TimeoutException` — не успели; `ExecutionException` — упали, причина в `getCause()`.
- После timeout не звоним `get()` второй раз без нового бюджета.
- `cancel(true)` — запрос на прерывание, а не убийство потока.
- При прерывании восстанавливаем флаг и делаем уборку в `finally`.
- `CountDownLatch` показывает, что задача реально завершилась после отмены.
- `supplyAsync` даёт результат, `thenApply` преобразует, `thenAccept` потребляет.
- `thenCompose` нужен для плоского future, когда следующая стадия сама асинхронная.
- `allOf` ждёт все future, но возвращает `Void`; данные берём из исходного списка.
- Порядок результатов сохраняется перебором future в порядке входных ID.
- Fail-fast не отдаёт частичные данные; частичный результат отдаёт успех и ошибки раздельно.
- CPU-bound пул ≈ `availableProcessors()`.
- Blocking I/O на platform threads требует больше потоков.
- Virtual threads хороши для множества ожиданий, но не ускоряют CPU.
- `parkNanos` в демо — модель ожидания; CPU-работа — отдельный цикл.
- Эксперимент с потоками — наблюдение, не полноценный benchmark.
- Общий deadline считается один раз от `System.nanoTime()`.
- Перед каждой стадией считается остаток времени.
- После timeout/ошибки задачу отменяют и дожидаются через latch.
- Structured concurrency управляет сроком жизни группы задач автоматически; в коде достаточно обычных `Future`.
