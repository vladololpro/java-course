## Задание 1. Прочитать stack trace

### Условие
Показать, как читать stack trace: определить тип исключения, сообщение, место возникновения и цепочку вызовов. Исправить причину ошибки, а не просто подавить исключение.

### Теория
- **Stack trace** — след стека вызовов, который JVM печатает при исключении.
- Первый элемент — место, где возникло исключение; последний — точка входа.
- `Throwable.getStackTrace()` возвращает массив `StackTraceElement`.
- `ArithmeticException` — unchecked-исключение, возникает, например, при делении на ноль.
- Ловить нужно конкретный тип исключения, а причину устранять в источнике.
- **Unchecked** означает, что компилятор не требует обязательной обработки такого исключения.

### Объяснение кода
- `StackTraceDemo.run()` вызывает цепочку `methodA → methodB → methodC → methodD`.
- В `methodD` выполняется деление `10 / divisor`; при `divisor = 0` возникает `ArithmeticException`.
- `run` ловит исключение и передаёт его в `printTrace`.
- `printTrace` печатает:
  - имя класса исключения через `getClass().getName()`;
  - сообщение через `getMessage()`;
  - первый элемент `getStackTrace()[0]`;
  - всю цепочку вызовов.
- После анализа причины `run` повторно вызывает `methodA(5)`, поэтому деление проходит успешно.
- Смысл: ошибка исправлена изменением входных данных, а не пустым `catch`.

**Подробнее по шагам.**
1. `methodA(0)` вызывает `methodB(0)`, тот — `methodC(0)`, тот — `methodD(0)`.
2. В `methodD` выполняется `10 / 0`, JVM создаёт `ArithmeticException`.
3. Исключение начинает раскручивать стек: `methodD`, `methodC`, `methodB`, `methodA`, `run`.
4. В `run` стоит `catch (ArithmeticException e)`, поэтому исключение перехватывается.
5. `printTrace` показывает, где именно произошла ошибка и как программа к этому пришла.
6. Затем `run` вызывает `methodA(5)`, и деление проходит без ошибки.

**Почему это правильное исправление.** Причина была в делителе `0`, поэтому программа передаёт корректный делитель. Пустой `catch` просто скрыл бы ошибку, и программа могла бы продолжить работать с неверным результатом.

### Что могут спросить и как отвечать
**Как читать stack trace?**
Сверху вниз — чтобы найти место возникновения ошибки, снизу вверх — чтобы понять, какая цепочка вызовов к ней привела.

**Почему `ArithmeticException` unchecked?**
Потому что это наследник `RuntimeException`. Компилятор не требует её обязательно обрабатывать, хотя перехватить её можно.

**Почему нельзя просто подавить исключение?**
Потому что причина ошибки останется. Программа может продолжить работу с неправильными данными или упасть позже в другом месте.

**Где в trace находится точка входа?**
В последнем элементе цепочки. В демо это `Main.main`.

**Чем `Error` отличается от исключения?**
`Error` обычно означает серьёзную проблему JVM или окружения, после которой восстановление часто невозможно. `Exception` можно обработать.

### Построчный разбор кода

Ключевой файл: `java2/errors/StackTraceDemo.java`.

```java
public void run() {                                          // 1
    try {                                                    // 2
        methodA(0);                                          // 3
    } catch (ArithmeticException e) {                        // 4
        printTrace(e);                                       // 5
    }                                                        // 6

    System.out.println("После исправления причины:");        // 7
    System.out.println("Результат: " + methodA(5));          // 8
}                                                            // 9

private void printTrace(ArithmeticException e) {             // 10
    System.out.println("Тип: " + e.getClass().getName());    // 11
    System.out.println("Сообщение: " + e.getMessage());      // 12
    System.out.println("Где: " + e.getStackTrace()[0]);      // 13
    for (StackTraceElement element : e.getStackTrace()) {    // 14
        System.out.println("  at " + element);               // 15
    }                                                        // 16
}                                                            // 17

private int methodD(int divisor) {                           // 18
    return 10 / divisor;                                     // 19
}                                                            // 20
```

1. `run` — точка входа демонстрации; показывает и ошибку, и исправленный вызов.
2. `try` — блок, в котором ожидается возможная ошибка.
3. `methodA(0)` — передаёт ноль; цепочка вызовов дойдёт до деления на ноль.
4. `catch (ArithmeticException e)` — ловит именно арифметическую ошибку, а не любое исключение.
5. `printTrace(e)` — передаёт пойманное исключение в метод анализа.
6. `}` — конец обработки ошибки.
7. Печать пояснения: дальше будет повторный вызов с корректными данными.
8. `methodA(5)` — причина исправлена: делитель больше не ноль, результат вычисляется.
9. `}` — конец `run`.
10. `printTrace` — метод, который показывает структуру stack trace.
11. `getClass().getName()` — полное имя класса исключения.
12. `getMessage()` — текст сообщения исключения.
13. `getStackTrace()[0]` — первый элемент, то есть место непосредственного возникновения.
14. Цикл по всем элементам stack trace.
15. Печать одного кадра стека: класс, метод, файл и строка.
16. `}` — конец цикла.
17. `}` — конец `printTrace`.
18. `methodD` — последний метод цепочки, где выполняется опасная операция.
19. `10 / divisor` — при `divisor == 0` JVM создаёт `ArithmeticException`.
20. `}` — конец `methodD`; остальные методы `methodC/B/A` просто передают вызов дальше.

## Задание 2. Checked или unchecked

### Условие
Классифицировать типовые ситуации на checked-исключения, unchecked-исключения и `Error`.

### Теория
- **Checked** — наследники `Exception`, но не `RuntimeException`. Компилятор требует обработки или объявления `throws`.
- **Unchecked** — наследники `RuntimeException`. Обычно означают ошибку программиста.
- **Error** — наследники `Error`; обычно восстановление невозможно (`OutOfMemoryError`).
- Checked-ошибки можно предвидеть и восстановить; unchecked — баг в коде.
- Иерархия: `Throwable` → `Exception`/`Error`; `Exception` → `RuntimeException` и checked-исключения.

### Объяснение кода
- `ExceptionClassifier.run()` формирует список из 11 ситуаций.
- Для каждой ситуации `classify(String)` возвращает категорию и краткое решение.
- Примеры:
  - неверный аргумент → `IllegalArgumentException` (unchecked);
  - отсутствующий файл → `FileNotFoundException`/`IOException` (checked);
  - нарушение состояния → `IllegalStateException` (unchecked);
  - сетевой отказ и занятый файл → `IOException` (checked);
  - нехватка памяти → `OutOfMemoryError` (Error);
  - ошибка парсинга числа → `NumberFormatException` (unchecked);
  - деление на ноль → `ArithmeticException` (unchecked);
  - `null` → `NullPointerException` (unchecked).
- Неизвестная ситуация даёт результат «Неизвестно».
- В демо классификация идёт по подстрокам, это учебная эвристика; в реальном коде классифицируют по типу исключения.

**Подробнее по шагам.**
1. `run` создаёт список строк с описанием ситуаций.
2. Для каждой строки вызывается `classify`.
3. Внутри `classify` проверяются ключевые слова через `contains`: «аргумент», «файл», «нарушение», «сеть» и т.д.
4. На основании этого возвращается категория и пример исключения.
5. Если ни одно условие не совпало, возвращается «Неизвестно».

**Важная оговорка.** Это демонстрация классификации, а не промышленный анализ. В реальном коде смотрят на тип пойманного исключения, а не на текст сообщения.

### Что могут спросить и как отвечать
**Чем checked отличается от unchecked?**
Checked-исключения компилятор требует обрабатывать или объявлять в `throws`. Unchecked-исключения не требуют этого, обычно это ошибки программиста.

**Почему `NumberFormatException` unchecked?**
Он наследуется от `IllegalArgumentException`, а тот — от `RuntimeException`. Поэтому компилятор не заставляет его обрабатывать.

**Почему `IOException` checked?**
Это внешняя ошибка ввода-вывода, которую можно предвидеть и обработать: повторить чтение, сообщить пользователю, закрыть ресурс. Компилятор требует, чтобы код это учитывал.

**Когда используют `Error`?**
Когда проблема серьёзная и обычно не связана с логикой приложения: нехватка памяти, сбой JVM. Такие ошибки чаще не обрабатывают, а логируют и завершают работу.

**`OutOfMemoryError` — это исключение?**
Это `Error`, а не `Exception`. Оно наследуется от `Throwable`, но не от `Exception`.

### Построчный разбор кода

Ключевой файл: `java2/errors/ExceptionClassifier.java`.

```java

    "Деление на ноль"                                       // 5
```

3. Отсутствующий файл — пример checked-ошибки ввода-вывода.
4. Нехватка памяти — пример `Error`, а не обычного исключения.
5. Деление на ноль — пример unchecked-арифметической ошибки.
6. `);` — список готов; в полном файле 11 ситуаций, ниже показаны четыре представителя.
7. Цикл по всем ситуациям.
8. Печать исходного описания ситуации.
9. `classify(s)` — получает категорию и пример исключения.
10. `}` — конец цикла.
11. `classify` — учебная функция классификации по ключевым словам.
12. Проверка слова «аргумент»: так определяется `IllegalArgumentException`.
13. `Unchecked` — компилятор не требует обработки, обычно это баг.
14. Проверка отсутствующего файла: это checked `FileNotFoundException`.
15. `Checked` — ошибку можно предвидеть и обработать.
16. Проверка нехватки памяти.
17. `Error` — восстановление обычно невозможно, это не `Exception`.
18. Проверка деления на ноль.
19. `Unchecked` — `ArithmeticException` наследуется от `RuntimeException`.
20. `}` — конец цепочки условий.
21. Если ни одно слово не совпало, возвращается «Неизвестно».
22. `}` — конец метода; в реальном коде классифицируют по типу исключения, а не по тексту.

## Задание 3. Собственное исключение

### Условие
Создать собственное бизнес-исключение для отказа в зачислении, показать его поля, сообщение и оборачивание системной ошибки с сохранением `cause`.

### Теория
- Своё исключение позволяет отделить бизнес-ошибку от системной.
- Наследование от `RuntimeException` делает исключение unchecked: вызывающий код не обязан его объявлять.
- Поля исключения дают программный доступ к деталям ошибки.
- `cause` сохраняет исходную причину при оборачивании.
- **Бизнес-исключение** описывает ожидаемое нарушение правил предметной области.

### Объяснение кода
- `EnrollmentRejectedException extends RuntimeException` содержит:
  - `studentId`, `courseId`, `reasonCode`;
  - конструкторы на 3 и 4 аргумента;
  - геттеры.
- Сообщение формируется в конструкторе: `"Enrollment rejected. Reason: " + reasonCode`.
- `OwnExceptionDemo.enroll(...)` всегда бросает это исключение.
- В первом случае причина `CAPACITY_FULL`, `cause == null`.
- Во втором случае причина `PREREQUISITE_MISSING`, а `cause` — `IllegalStateException("Database is down")`.
- Второй случай показывает, что бизнес-исключение может оборачивать системную ошибку, не теряя её.

**Подробнее по шагам.**
1. `enroll` вызывается с `simulateCause = false`. Создаётся `EnrollmentRejectedException` с кодом `CAPACITY_FULL` и без причины.
2. Клиент может поймать исключение и прочитать `getReasonCode()`, чтобы показать понятное сообщение.
3. Затем `enroll` вызывается с `simulateCause = true`. Внутри создаётся системная ошибка `Database is down`.
4. Она передаётся в конструктор бизнес-исключения как `cause`.
5. Теперь у клиента есть и бизнес-причина `PREREQUISITE_MISSING`, и техническая причина `Database is down`.

**Зачем нужны конструкторы на 3 и 4 аргумента.** Первый удобен, когда причины нет. Второй — когда нужно сохранить исходное исключение.

### Что могут спросить и как отвечать
**Почему исключение наследуется от `RuntimeException`?**
Потому что это бизнес-отказ, который не должен заставлять каждый вызывающий метод объявлять `throws`. Его можно обработать там, где это действительно нужно.

**Зачем передавать `cause`?**
Чтобы не потерять исходную техническую причину. Без `cause` пришлось бы угадывать, почему произошёл отказ.

**Зачем нужны поля `studentId`, `courseId`, `reasonCode`?**
Чтобы клиент мог программно обработать отказ: показать, кого и куда не зачислили, и выбрать действие по коду причины.

**Чем бизнес-исключение отличается от технического?**
Бизнес-исключение описывает нарушение правил предметной области. Техническое — сбой инфраструктуры: базы данных, сети, файловой системы.

**Почему сообщение формируется в конструкторе?**
Чтобы исключение всегда имело понятное и одинаковое сообщение, независимо от места создания.

### Построчный разбор кода

Ключевые файлы: `java2/errors/EnrollmentRejectedException.java`, `java2/errors/OwnExceptionDemo.java`.

```java
public class EnrollmentRejectedException extends RuntimeException { // 1
    private final long studentId;                                  // 2
    private final long courseId;                                   // 3
    private final String reasonCode;                               // 4

    public EnrollmentRejectedException(long studentId, long courseId, String reasonCode) { // 5
        super("Enrollment rejected. Reason: " + reasonCode);       // 6
        this.studentId = studentId;                                // 7
        this.courseId = courseId;                                  // 8
        this.reasonCode = reasonCode;                              // 9
    }                                                              // 10

    public EnrollmentRejectedException(long studentId, long courseId, String reasonCode, Throwable cause) { // 11
        super("Enrollment rejected. Reason: " + reasonCode, cause); // 12
        this.studentId = studentId;                                // 13
        this.courseId = courseId;                                  // 14
        this.reasonCode = reasonCode;                              // 15
    }                                                              // 16
}                                                                  // 17

private void enroll(long studentId, long courseId, boolean simulateCause) { // 18
    if (simulateCause) {                                           // 19
        throw new EnrollmentRejectedException(studentId, courseId, // 20
            "PREREQUISITE_MISSING",                                // 21
            new IllegalStateException("Database is down"));        // 22
    }                                                              // 23
    throw new EnrollmentRejectedException(studentId, courseId, "CAPACITY_FULL"); // 24
}                                                                  // 25
```

1. `extends RuntimeException` — бизнес-исключение unchecked; вызывающий код не обязан объявлять `throws`.
2. `studentId` — поле для программной обработки отказа.
3. `courseId` — второй идентификатор, кого и куда не зачислили.
4. `reasonCode` — стабильный код причины, удобный для сравнения.
5. Конструктор без причины — для обычного бизнес-отказа.
6. `super(...)` — формирует сообщение исключения через конструктор родителя.
7. Сохраняет студента.
8. Сохраняет курс.
9. Сохраняет код причины.
10. `}` — конец первого конструктора.
11. Конструктор с `Throwable cause` — для оборачивания технической ошибки.
12. `super(message, cause)` — сохраняет и сообщение, и исходную причину.
13. Сохраняет студента.
14. Сохраняет курс.
15. Сохраняет код причины.
16. `}` — конец второго конструктора.
17. `}` — конец класса; геттеры позволяют прочитать поля.
18. `enroll` — демонстрационный метод, который всегда бросает отказ.
19. `simulateCause` — выбирает сценарий: с технической причиной или без.
20. Создаётся бизнес-исключение с кодом `PREREQUISITE_MISSING`.
21. Код причины показывает, какое правило нарушено.
22. `new IllegalStateException(...)` передаётся как `cause`; техническая причина не теряется.
23. `}` — конец ветки с причиной.
24. В обычном сценарии бросается отказ `CAPACITY_FULL` без `cause`.
25. `}` — конец метода.

## Задание 4. try-catch-finally

### Условие
Показать порядок выполнения `try`, `catch`, `finally`, а также опасность `return` в `finally`.

### Теория
- `finally` выполняется всегда: и при обычном выходе, и при `return`, и при исключении.
- Если в `finally` написать `return`, он перезапишет возвращаемое значение и скроет исходное исключение.
- Это не suppressed-исключение, а именно потерянное/отброшенное исключение.
- В рабочем коде `return` в `finally` — антипаттерн.
- `finally` используют для освобождения ресурсов, а не для изменения результата.

### Объяснение кода
В `TryCatchFinallyDemo` четыре сценария:
1. `returnFromTry()` — `return "try"` в `try`, затем выполняется `finally`; результат `"try"`.
2. `returnFromCatch()` — исключение в `try`, `return "catch"` в `catch`, затем `finally`; результат `"catch"`.
3. `hideException()` — исключение в `try`, но `return "finally"` в `finally`; исходное исключение теряется, результат `"finally"`.
4. `throwFromTry()` — исключение в `try`, `finally` без `return`; исключение пробрасывается наружу и ловится снаружи.

**Подробнее по шагам.**
1. В первом случае `try` вычисляет `return "try"`, но перед фактическим возвратом выполняется `finally`.
2. Во втором случае в `try` возникает исключение, управление переходит в `catch`, там вычисляется `return "catch"`, затем выполняется `finally`.
3. В третьем случае в `try` возникает исключение, но `finally` делает `return "finally"`. Этот `return` подавляет исключение и становится результатом метода.
4. В четвёртом случае `finally` просто выполняет очистку и не делает `return`, поэтому исключение уходит наружу.

**Почему третий случай опасен.** Исходная ошибка полностью исчезает. Программа может решить, что всё нормально, хотя на самом деле произошёл сбой.

### Что могут спросить и как отвечать
**В каком порядке выполняются блоки?**
Сначала `try`. Если возникло исключение — `catch`. Затем всегда `finally`.

**Почему `return` в `finally` опасен?**
Он перезаписывает результат и может скрыть исключение. Ошибка теряется, и вызывающий код не узнает о сбое.

**Чем потерянное исключение отличается от suppressed?**
Потерянное исключение просто отбрасывается. Suppressed-исключение прикрепляется к основному и доступно через `getSuppressed()`.

**Как правильно освобождать ресурсы?**
Лучше использовать try-with-resources. Если ресурс не реализует `AutoCloseable`, освобождать его в `finally` без `return`.

**Выполнится ли `finally`, если в `try` был `return`?**
Да, `finally` выполняется перед фактическим выходом из метода.

## Задание 5. Try-with-resources и suppressed

### Условие
Показать автоматическое закрытие ресурса, закрытие при исключении и подавленное исключение из `close()`.

### Теория
- Ресурс, реализующий `AutoCloseable`, можно открыть в `try-with-resources`.
- Ресурс закрывается автоматически при выходе из `try`.
- Если основное исключение уже возникло, а `close()` тоже бросает исключение, ошибка закрытия добавляется как **suppressed**.
- Достать её можно через `Throwable.getSuppressed()`.
- Suppressed не заменяет основное исключение, а дополняет его.

### Объяснение кода
- `TestResource implements AutoCloseable`:
  - конструктор печатает `[OPEN]`;
  - `use()` печатает `[USE]`;
  - `close()` печатает `[CLOSE]` и при `failOnClose` бросает `RuntimeException`.
- `AutoCloseableDemo.run()` показывает три сценария:
  1. успешное выполнение — ресурс открывается, используется и закрывается;
  2. исключение в работе — ресурс всё равно закрывается, затем срабатывает `catch`;
  3. исключение и в работе, и в `close()` — основным остаётся ошибка работы, ошибка закрытия попадает в suppressed.
- В третьем сценарии suppressed выводится через `getSuppressed()`.

**Подробнее по шагам.**
1. В `try (TestResource resource = new TestResource(...))` ресурс создаётся и попадает под автоматическое управление.
2. Если внутри `try` всё хорошо, после блока вызывается `close()`.
3. Если внутри `try` возникает исключение, `close()` всё равно вызывается перед выходом в `catch`.
4. Если `close()` тоже падает, JVM не заменяет основное исключение, а добавляет ошибку закрытия в список suppressed.
5. В `catch` можно получить основное исключение и перебрать `getSuppressed()`, чтобы увидеть ошибку закрытия.

**Что будет, если основного исключения нет.** Тогда исключение из `close()` станет основным, потому что подавлять его нечем.

### Что могут спросить и как отвечать
**Зачем нужен try-with-resources?**
Он гарантирует закрытие ресурса и сокращает код. Не нужно вручную писать `finally` с `close()`.

**Что такое `AutoCloseable`?**
Это интерфейс с методом `close()`. Ресурсы, которые нужно закрывать, реализуют его.

**Что такое suppressed-исключение?**
Это второстепенная ошибка, которая возникла на фоне основной. Она сохраняется в основном исключении и доступна через `getSuppressed()`.

**Почему `close()` вызывается до `catch`?**
Потому что try-with-resources закрывает ресурс при выходе из `try`, а `catch` выполняется уже после этого.

**Что будет, если `close()` упадёт без основного исключения?**
Исключение из `close()` станет основным и будет проброшено наружу.

### Построчный разбор кода

Ключевой файл: `java2/errors/AutoCloseableDemo.java`.

## Задание 6. Граница перевода исключения

### Условие
Перехватить низкоуровневое `NumberFormatException` и перевести его в бизнес-исключение `CourseImportException` с номером записи и сохранённым `cause`.

### Теория
- **Перевод исключения** — замена низкоуровневой ошибки на понятную бизнес-ошибку.
- При переводе обязательно сохранять исходное исключение в `cause`.
- Ловить нужно конкретный тип, а не общий `Exception`.
- `CourseImportException` — checked-исключение, поэтому его нужно обрабатывать или объявлять.
- Перевод нужен на границе слоя: внутри можно работать с техническими ошибками, наружу отдавать доменные.

### Объяснение кода
- `ExceptionTranslationDemo.importRecord(String input, int recordNumber)` вызывает `Integer.parseInt(input)`.
- Если ввод не число, возникает `NumberFormatException`.
- Метод ловит именно `NumberFormatException` и бросает `CourseImportException` с номером записи и исходной причиной.
- `CourseImportException` хранит `recordNumber`, `processedRecords`, `errorCode` и `cause`.
- В `run` первым вызывается `importRecord("JAVA-101", 1)`. Строка `JAVA-101` не является числом, поэтому исключение возникает уже на записи 1, а второй вызов не выполняется.
- Фактический вывод: `Ошибка: Import failed at record 1: Invalid number format`, `Запись №: 1`, `Причина: NumberFormatException`.
- Смысл: клиент получает бизнес-ошибку импорта, но не теряет исходную техническую причину.

**Подробнее по шагам.**
1. `importRecord` пытается преобразовать строку в число через `Integer.parseInt`.
2. Если строка не является числом, `parseInt` бросает `NumberFormatException`.
3. `catch (NumberFormatException e)` перехватывает именно эту ошибку.
4. Вместо неё создаётся `CourseImportException` с номером записи, сообщением и `cause = e`.
5. Вызывающий код получает ошибку уровня импорта и может обработать её по правилам бизнес-логики.
6. Исходная причина остаётся доступной через `getCause()`.

**Почему не `catch (Exception)`.** Общий `catch` поймал бы и другие ошибки, которые не относятся к парсингу. Это могло бы скрыть баг или неправильно классифицировать проблему.

### Что могут спросить и как отвечать
**Зачем переводить исключение?**
Чтобы на границе слоя отдать понятную бизнес-ошибку и не раскрывать низкоуровневые детали. При этом `cause` сохраняет техническую причину для диагностики.

**Почему нельзя просто напечатать ошибку?**
Потому что вызывающий код не сможет её обработать. Печать в консоль не останавливает выполнение и не сообщает клиенту, что импорт не удался.

**Зачем `cause`?**
Чтобы сохранить исходное исключение и его stack trace. Без него потеряется информация, где и почему возникла ошибка.

**Почему `CourseImportException` checked?**
Это инфраструктурная ошибка импорта, которую вызывающий код должен явно обработать или объявить. Checked-исключение заставляет об этом подумать.

**Почему ловим именно `NumberFormatException`?**
Потому что мы знаем, какую операцию выполняем и какая ошибка возможна. Конкретный `catch` не скрывает другие проблемы.

## Задание 7. Ошибка как значение: Optional, результат-значение, unchecked

### Условие
Показать три подхода: `Optional` для нормального отсутствия, результат-значение для ожидаемого бизнес-отказа, unchecked-исключение для нарушения контракта.

### Теория
- `Optional` используют, когда отсутствие значения — нормальная ситуация.
- Результат-значение (`record`/специальный класс) используют для ожидаемого бизнес-отказа.
- Исключение используют для бага или нарушения контракта.
- Не стоит использовать исключения для обычного ветвления бизнес-логики.
- **Контракт** — набор правил, которые метод обещает соблюдать.

### Объяснение кода
- `ResultDemo.findCourse(long id)` возвращает `Optional<String>`: курс есть или его нормально нет.
- `parseCourse(String raw)` возвращает `Optional<CourseCode>`: неверный код — нормальный случай.
- `parseCourse` сначала вызывает `CourseCode.isValid`, затем `parse`, поэтому `null` и неверный формат дают `Optional.empty()`.
- `enroll(...)` возвращает вложенный `record EnrollmentResult(boolean accepted, String reasonCode)`.
  - Отказ — это бизнес-результат, а не исключение.
- `calculatePrice(int price)` бросает `IllegalArgumentException`, если цена отрицательная.
  - Отрицательная цена — нарушение контракта, баг вызывающего кода.

**Подробнее по шагам.**
1. `findCourse` проверяет `id`. Если курс найден, возвращает `Optional.of(...)`, иначе `Optional.empty()`.
2. `parseCourse` не бросает исключение на неверный ввод, потому что неверный код — ожидаемая ситуация. Он возвращает пустой `Optional`.
3. `enroll` проверяет правила зачисления и возвращает `EnrollmentResult` с `accepted` и `reasonCode`.
4. Клиент смотрит на `accepted()` и решает, что делать. Это обычная бизнес-логика, а не аварийная ситуация.
5. `calculatePrice` проверяет цену. Если она отрицательная, это ошибка программиста, поэтому бросается `IllegalArgumentException`.
6. `printEnrollment` печатает результат зачисления, не используя исключения для управления потоком.

**Почему это разные инструменты.** `Optional` — про отсутствие значения. Результат-значение — про ожидаемый исход операции. Исключение — про нарушение контракта или невозможность продолжать.

### Что могут спросить и как отвечать
**Когда использовать `Optional`, а когда исключение?**
`Optional` — когда отсутствие значения нормально и его нужно явно обработать. Исключение — когда произошла ошибка или нарушение контракта, после которого обычное продолжение невозможно.

**Почему отказ в зачислении — не исключение?**
Потому что отказ — ожидаемый бизнес-результат. Клиент должен уметь обработать его как обычный исход, а не как аварию.

**Почему отрицательная цена — исключение?**
Отрицательная цена нарушает контракт метода. Это ошибка вызывающего кода, которую нужно исправить, а не штатный бизнес-сценарий.

**Чем `record` удобен для результата?**
Он кратко описывает набор значений, автоматически создаёт конструктор и геттеры, хорошо подходит для неизменяемого результата операции.

**Почему `parseCourse` не бросает исключение?**
Неверный код курса — нормальная ситуация при вводе. Поэтому метод возвращает `Optional.empty()`, а не аварийно завершается.

## Задание 10. Параметризованный тест

### Условие
Проверить нормализацию и валидацию кода курса: обрезка пробелов, приведение к верхнему регистру, формат `[A-Z]{2,4}-\d{3}`. Однотипные проверки оформить параметризованно.

### Теория
- `@ParameterizedTest` запускает один тест на нескольких наборах данных.
- `@CsvSource`, `@ValueSource`, `@NullSource` задают источники значений.
- `name` в аннотации делает имя запуска понятным.
- `Locale.ROOT` нужен, чтобы `toUpperCase` не зависел от локали.

### Объяснение кода
- `CourseCode.parse(String raw)`:
  - `null` → `IllegalArgumentException("Course code is null")`;
  - иначе `trim()` и `toUpperCase(Locale.ROOT)`;
  - затем проверка регулярным выражением `[A-Z]{2,4}-\d{3}`;
  - при несоответствии — `IllegalArgumentException`.
- `CourseCode.isValid(String raw)`:
  - `null` → `false`;
  - иначе та же нормализация и проверка.
- `Task10Test`:
  - `@CsvSource` с 4 валидными парами;
  - отдельный тест на обрезку пробелов;
  - `@ValueSource` с 7 невалидными значениями;

2. Затем строка очищается от пробелов по краям и приводится к верхнему регистру.
3. После нормализации проверяется шаблон. `java-101` становится `JAVA-101` и проходит.
4. Если шаблон не совпал, бросается `IllegalArgumentException`.
5. Параметризованный тест подставляет разные входы и ожидаемые результаты в один и тот же код проверки.

**Почему `Locale.ROOT`.** В некоторых локалях преобразование регистра работает иначе. `Locale.ROOT` задаёт нейтральные правила и делает поведение предсказуемым.

### Что могут спросить и как отвечать
**Зачем параметризованные тесты?**
Они позволяют проверить много входных данных без копирования одного и того же теста. Меньше дублирования, больше покрытие.

**Чем `@CsvSource` отличается от `@ValueSource`?**
`@ValueSource` передаёт одно значение за запуск. `@CsvSource` передаёт строку CSV, которую можно разобрать на несколько параметров.

**Почему `Locale.ROOT`?**
Чтобы `toUpperCase` не зависел от локали пользователя или системы. Например, в турецкой локали буква `i` преобразуется особым образом.

**Почему `null` вынесен в отдельный источник?**
`@NullSource` явно передаёт `null`. Это позволяет проверить обработку `null` отдельно и не смешивать её с обычными невалидными строками.

11. Создаётся валидный объект с нормализованным значением.
12. `}` — конец `parse`.
13. `isValid` — проверочный метод, не бросающий исключение на обычный неверный ввод.

2. Затем запрашивается 100 часов, хотя осталось только 22.
3. Метод проверяет превышение до изменения `completedHours`, поэтому бросает исключение и не меняет прогресс.
4. Тест ловит исключение через `assertThrows` и проверяет сообщение.
5. Отдельно проверяется, что `completedHours()` всё ещё равно `10`.
6. В тесте с `EnrollmentService` проверяется не только тип исключения, но и его поля, чтобы клиент мог обработать отказ программно.

**Почему это хороший тест.** Он проверяет не только факт ошибки, но и её содержание, и то, что объект не остался в частично изменённом состоянии.

### Что могут спросить и как отвечать
**Зачем проверять сообщение и поля исключения?**
Чтобы убедиться, что ошибка содержит полезную информацию. Поля нужны для программной обработки, сообщение — для диагностики и пользователя.

**Что возвращает `assertThrows`?**
Объект пойманного исключения. Это позволяет проверить `getMessage()`, поля и `getCause()`.

**Почему важно проверять состояние после ошибки?**
Операция не должна оставлять объект в частично изменённом состоянии. Иначе после ошибки данные будут противоречивыми.

**Чем `assertThrows` отличается от `assertDoesNotThrow`?**
`assertThrows` ожидает исключение и проверяет его. `assertDoesNotThrow` проверяет, что код завершился без исключения.

**Что такое атомарность операции?**
Это свойство, при котором операция либо выполняется полностью, либо не меняет состояние. В тесте `completeHours` при ошибке прогресс остаётся прежним.

## Задание 12. Хрупкие тесты

### Условие
Показать, как избегать хрупких тестов: независимость от порядка запуска, общего `static`-состояния, текущей рабочей директории и полного `toString()`.

### Теория
- Хрупкий тест падает при изменении окружения, порядка запуска или незначительной детали реализации.
- Тесты должны быть изолированы: каждый создаёт свои объекты.
- `@BeforeEach` помогает готовить свежее состояние перед каждым тестом.
- Нельзя полагаться на общий `static`-мутабельный state.
- Нельзя сравнивать полный `toString()`, если важны только отдельные поля.
- Нельзя зависеть от текущей рабочей директории и файлов по относительному пути.

### Объяснение кода
- `Task12And13Test` помечен `@TestMethodOrder(MethodOrderer.Random.class)`, чтобы порядок методов был случайным.
- `setUp()` с `@BeforeEach` создаёт новый `EnrollmentService` перед каждым тестом.
- `enroll_withFreshService_shouldNotShareState()` показывает, что два экземпляра сервиса не делят состояние.
- `EnrollmentService` не имеет полей, поэтому он stateless.
- В тестах используются локальные объекты и `StringReader` вместо общих файлов.
- Проверяются отдельные поля, а не полный `toString()`.
- Исходного `src/test/resources/junit-platform.properties` нет; случайный порядок задан аннотацией.

**Подробнее по шагам.**
1. JUnit создаёт новый экземпляр тестового класса для каждого метода.
2. `@BeforeEach` вызывает `setUp` и создаёт новый `EnrollmentService`.
3. Тест использует только локальные объекты, созданные внутри него.
4. Случайный порядок методов проверяет, что тесты не зависят от предыдущих запусков.
5. Если бы тесты использовали общий `static`-список или файл, результат зависел бы от порядка и окружения.
6. Проверка отдельных полей вместо `toString()` делает тест устойчивым к изменению формата вывода.

**Почему это важно.** Тест должен падать только тогда, когда сломано поведение, а не из-за порядка запуска или форматирования.

### Что могут спросить и как отвечать
**Почему тесты должны быть независимы от порядка?**
Потому что JUnit не гарантирует порядок методов. Если тест зависит от другого теста, он может падать случайно и усложнять диагностику.

**Зачем `@BeforeEach`?**
Чтобы перед каждым тестом подготовить свежее состояние и не делить данные между тестами.

**Чем плох общий `static`-state?**
Он сохраняется между тестами. Один тест может изменить данные, и другой начнёт работать в неожиданных условиях.

**Почему не стоит проверять весь `toString()`?**
Потому что формат строки может измениться без изменения поведения. Тест станет хрупким. Лучше проверять конкретные поля.

**Почему случайный порядок методов полезен?**
Он помогает обнаружить скрытые зависимости между тестами. Если тесты действительно изолированы, порядок не влияет на результат.

## Задание 14. Импорт и suppressed

### Условие
Реализовать импорт курсов из `Reader` через try-with-resources. При malformed-записи бросать `CourseImportException` с номером записи и числом обработанных записей. Ошибку закрытия сохранять как suppressed. Не возвращать частичный результат.

### Теория
- `Reader` читает символьные данные; `BufferedReader` удобно читает построчно.
- `try-with-resources` автоматически закрывает ресурс.
- `CourseImportException` — checked-исключение, поэтому оно объявляется в `throws`.
- **Suppressed**-исключение возникает, если `close()` падает при уже имеющемся основном исключении.
- Результат нужно собирать локально и возвращать только при полном успехе.
- **Malformed-запись** — строка, которая не соответствует ожидаемому формату.

### Объяснение кода
- `CourseImporter.importCourses(Reader reader)`:
  - открывает `BufferedReader` в try-with-resources;
  - считает `lineNumber` и `processedRecords`;
  - malformed-строка — та, где нет `":"`;
  - валидная строка добавляется в локальный список;
  - при malformed-строке бросает `CourseImportException` с номером записи и числом уже обработанных записей;
  - при `IOException` переводит её в `CourseImportException` с `cause`;
  - ошибка закрытия при наличии основного исключения попадает в suppressed.
- `CourseImportException` хранит `recordNumber`, `processedRecords`, `errorCode` и `cause`.
- `Task14Test` проверяет:
  - успешный импорт;
  - malformed-запись: `recordNumber = 3`, `processedRecords = 2`;
  - `FailingReader`, у которого `close()` бросает ошибку: она должна быть в `getSuppressed()`.
- Частичный список не возвращается: исключение прерывает метод.

**Подробнее по шагам.**
1. Метод создаёт локальный `result` и счётчик `processedRecords`.
2. `BufferedReader` читает файл построчно внутри try-with-resources.
3. Для каждой строки увеличивается `lineNumber`.
4. Если строка не содержит `":"`, создаётся `CourseImportException` с номером строки и количеством уже обработанных записей.
5. Валидная строка добавляется в `result`, счётчик увеличивается.
6. При `IOException` создаётся `CourseImportException` с кодом `IMPORT_IO_ERROR` и исходной ошибкой в `cause`.
7. Если `close()` тоже падает, его исключение добавляется как suppressed к основному.
8. Если всё прошло успешно, возвращается полный список. Частичный список наружу не отдаётся.

**Почему локальный результат.** Если вернуть частичный список, клиент может решить, что импорт прошёл успешно. Лучше явно сообщить об ошибке и не отдавать неполные данные.

### Что могут спросить и как отвечать
**Почему не возвращается частичный результат?**
Потому что неполные данные могут быть опасны. Клиент должен знать, что импорт не завершён, и обработать ошибку.

**Что такое `processedRecords`?**
Это количество строк, которые успешно обработаны до момента ошибки. Оно помогает понять, сколько данных уже прошло.

**Зачем сохранять `cause`?**
Чтобы не потерять исходную причину, например `IOException` с сообщением от файловой системы. Это нужно для диагностики.

**Что такое suppressed-исключение?**
Это ошибка, которая возникла при закрытии ресурса на фоне основной ошибки. Она прикрепляется к основной и доступна через `getSuppressed()`.

**Почему используется try-with-resources?**
Чтобы гарантированно закрыть `BufferedReader` и корректно обработать ошибку закрытия через suppressed.

**Что считается malformed-записью?**
В этой реализации — строка, в которой нет `":"`. В реальном формате проверка была бы строже.

## Задание 15. Use case импорта и зачисления

### Условие
Разделить уровни ошибок в use case зачисления и импорта:
- ошибка программиста — `IllegalArgumentException`;
- ожидаемый бизнес-отказ — `EnrollmentRejectedException` со стабильным кодом;
- инфраструктурная ошибка — `CourseImportException` с `cause`;
- ресурсы закрывать через try-with-resources, ошибку закрытия сохранять как suppressed;
- не использовать общий `catch (Exception)`.

### Теория
- У разных ошибок разная природа и разная реакция клиента.
- **Programming error** — баг вызывающего кода, исправляется программистом.
- **Business rejection** — ожидаемый отказ, его обрабатывают как результат.
- **Infrastructure error** — сбой внешней среды, его оборачивают и сохраняют причину.
- Общий `catch (Exception)` скрывает детали и мешает различать уровни ошибок.
- `ErrorCode` даёт стабильные коды для бизнес-отказов и импорта.

### Объяснение кода
- `EnrollmentService.enroll(...)`:
  - сначала проверяет `studentId <= 0 || courseId <= 0` и бросает `IllegalArgumentException` с кодом `INVALID_STUDENT_OR_COURSE`;
  - затем бизнес-правила в порядке: `ARCHIVED` → `CLOSED` → `ALREADY_ENROLLED` → `PREREQUISITE_MISSING` → `NO_SEATS`;
  - отказ бросает `EnrollmentRejectedException` со стабильным `reasonCode`.
- `CourseImporter.importCourses(...)`:
  - malformed-запись → `CourseImportException` с кодом `IMPORT_MALFORMED_RECORD`;
  - `IOException` → `CourseImportException` с кодом `IMPORT_IO_ERROR` и `cause`;
  - ошибка закрытия сохраняется как suppressed.
- `Task15Test` содержит 22 запуска:
  - валидное и невалидное зачисление;
  - таблицу бизнес-правил;
  - проверку полей исключения;
  - успешный импорт;
  - malformed-записи;
  - ошибку чтения с сохранением `cause`;
  - suppressed-ошибку закрытия;
  - повторный импорт после ошибки.
- В бизнес-коде не используется общий `catch (Exception)`: ловятся конкретные типы.

**Подробнее по шагам.**
1. `EnrollmentService` сначала проверяет корректность идентификаторов. Если они неверные, это ошибка программиста, поэтому `IllegalArgumentException`.
2. Затем проверяются бизнес-правила. Если студент не подходит, это ожидаемый отказ, поэтому `EnrollmentRejectedException` с кодом.
3. `CourseImporter` работает с внешним ресурсом. Ошибки чтения и формата — это инфраструктурные проблемы, поэтому `CourseImportException`.
4. `CourseImportException` объявлен checked, потому что вызывающий код обязан обработать сбой импорта.
5. `EnrollmentRejectedException` unchecked, потому что бизнес-отказ можно обработать как обычный результат, не заставляя каждый метод объявлять `throws`.
6. Ошибка закрытия ресурса не заменяет основную, а сохраняется как suppressed.
7. Тесты проверяют все уровни отдельно: ошибки программиста, бизнес-отказы, инфраструктурные ошибки и повторный импорт после сбоя.

**Почему не общий `catch (Exception)`.** Он смешивает разные категории ошибок и часто приводит к тому, что баги программиста маскируются под бизнес-ошибки. Ловить нужно конкретные типы на нужном уровне.

### Что могут спросить и как отвечать
**Зачем разделять ошибки на уровни?**
Чтобы каждый слой обрабатывал только свои ошибки. Бизнес-код не должен знать детали файловой системы, а инфраструктурный код не должен решать бизнес-правила.

**Почему `IllegalArgumentException` — не бизнес-отказ?**
Потому что неверные `studentId` или `courseId` — ошибка вызывающего кода. Это баг, а не ожидаемое правило предметной области.

**Почему `EnrollmentRejectedException` unchecked, а `CourseImportException` checked?**
Бизнес-отказ — ожидаемый результат, его можно обработать там, где нужно, без обязательного `throws`. Импорт — внешняя операция, которая может не удаться, поэтому компилятор требует её явно обработать.

**Зачем стабильные `ErrorCode`?**
Чтобы клиенты и тесты могли реагировать на конкретную причину, не сравнивая текст сообщения. Коды не должны меняться при изменении формулировок.

**Как проверить suppressed-ошибку?**
Поймать основное исключение и вызвать `getSuppressed()`. В массиве должна быть ошибка, возникшая при закрытии ресурса.

**Почему после ошибки импорт снова работает?**
Потому что `CourseImporter` не хранит состояние между вызовами. Результат и счётчики локальны, поэтому новый вызов начинает с чистого листа.

**Где здесь try-with-resources?**
В `CourseImporter.importCourses`: `BufferedReader` открывается в try-with-resources и закрывается автоматически.

## Краткая шпаргалка по JUnit 5 и исключениям
