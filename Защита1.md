## Задание 1. Один контракт, две реализации

### Условие
Нужно показать, что переменная интерфейсного типа может хранить разные реализации, а конкретный метод выбирается во время выполнения по фактическому типу объекта.

### Теория
- **Интерфейс** задаёт контракт: какие методы обязаны реализовать классы. Он не хранит состояние и описывает роль объекта.
- **Статический тип** — тип переменной, который видит компилятор. По нему проверяется, существует ли вызываемый метод.
- **Динамический тип** — реальный класс объекта. По нему JVM выбирает, какую реализацию метода вызвать.
- **Полиморфизм** — один и тот же вызов может работать по-разному в зависимости от фактического объекта.
- `@Override` помогает компилятору проверить, что метод действительно переопределяет метод интерфейса или родителя.

### Объяснение кода
- `CourseFormatter` — интерфейс с методом `String format(Course course)`.
- `CompactCourseFormatter` возвращает короткую строку, `DetailedCourseFormatter` — подробную.
- В `Main` создаётся `Course`, затем одна переменная `CourseFormatter formatter` последовательно указывает на разные реализации.
- Вызов `formatter.format(course)` компилируется, потому что метод есть в типе `CourseFormatter`. JVM вызывает реализацию того класса, объект которого сейчас лежит в переменной.
- Если убрать `format` из интерфейса, компилятор выдаст ошибки и в реализациях, и в `Main`, хотя сами методы в классах останутся. Это доказывает, что компилятор смотрит на статический тип.
- В эксперименте из `Answers1.md` удаление метода даёт ровно 4 ошибки: по одной `method does not override or implement a method from a supertype` в обеих реализациях и две `cannot find symbol` для `formatter.format(course)` в `Main`.

**Подробнее по шагам.**
1. `CourseFormatter formatter = new CompactCourseFormatter();` — компилятор видит переменную типа `CourseFormatter`, а объект создаётся класса `CompactCourseFormatter`.
2. `formatter.format(course)` — компилятор проверяет только, что `format(Course)` объявлен в `CourseFormatter`.
3. JVM во время выполнения смотрит на объект внутри переменной и вызывает именно `CompactCourseFormatter.format`.
4. После `formatter = new DetailedCourseFormatter();` тот же вызов начинает работать иначе, хотя код вызова не изменился.

**Почему это важно.** Клиентский код зависит только от интерфейса и не знает о конкретных классах. Это основа подменяемости реализаций.

### Что могут спросить и как отвечать
**Что такое полиморфизм?**
Полиморфизм — это возможность работать с объектами разных классов через общий тип и получать разное поведение при одном и том же вызове. Здесь общий тип — `CourseFormatter`, а поведение зависит от реализации.

**Чем статический тип отличается от динамического?**
Статический тип — это тип переменной в исходном коде, его видит компилятор. Динамический тип — реальный класс объекта во время выполнения, его использует JVM для выбора метода.

**Почему здесь нужен интерфейс, а не абстрактный класс?**
У форматтера нет общего состояния и общего кода, есть только контракт. Интерфейс не занимает единственное наследование класса, поэтому класс-форматтер может одновременно наследовать что-то другое и реализовывать другие интерфейсы.

**Что произойдёт, если метод интерфейса не реализовать?**
Класс, объявленный как `implements CourseFormatter`, должен реализовать все абстрактные методы, иначе компилятор выдаст ошибку.

**Где здесь dynamic dispatch?**
В строке `formatter.format(course)`: вызов один, но JVM выбирает реализацию по фактическому классу объекта, который лежит в переменной.

### Построчный разбор кода

Ниже — ключевой фрагмент из `CourseFormatter.java`, `CompactCourseFormatter.java`, `DetailedCourseFormatter.java` и `Main.java`. Комментарии добавлены только для защиты.

```java
public interface CourseFormatter {                    // 1
    String format(Course course);                     // 2
}                                                     // 3

formatter = new DetailedCourseFormatter();            // 9
System.out.println(formatter.format(course));         // 10
```

1. `public interface CourseFormatter` — объявляет контракт; клиенту достаточно знать, что у объекта есть метод `format`.
2. `String format(Course course)` — единственный метод контракта: принимает курс, возвращает строку.
3. `}` — закрывает интерфейс; здесь нет полей состояния, только описание роли.
4. `new Course(...)` — создаёт конкретный объект курса с id 10, названием и длительностью 32 часа.
5. `completeHours(6)` — меняет состояние курса: 6 часов уже пройдено.
6. `CourseFormatter formatter` — переменная интерфейсного типа; компилятор видит только метод `format`.
7. `new CompactCourseFormatter()` — создаёт компактную реализацию и кладёт её в переменную интерфейсного типа.
8. `formatter.format(course)` — компилятор разрешает вызов по типу `CourseFormatter`, а JVM выбирает реализацию по фактическому объекту `CompactCourseFormatter`.
9. `formatter = new DetailedCourseFormatter()` — в ту же переменную кладётся другая реализация; код вызова ниже не меняется.
10. Второй `formatter.format(course)` — тот же статический вызов, но dynamic dispatch выбирает уже `DetailedCourseFormatter.format`.

## Задание 2. Dynamic dispatch: override и overload

### Условие
Показать разницу между переопределением метода и перегрузкой: override выбирается по динамическому типу, overload — по статическому типу и типам аргументов.

### Теория
- **Override** — наследник объявляет метод с той же сигнатурой. Реализация выбирается во время выполнения по фактическому классу объекта.
- **Overload** — методы с одинаковым именем, но разными параметрами. Компилятор выбирает подходящий вариант по статическому типу ссылки и типам аргументов.
- **Сигнатура** — имя метода плюс типы параметров. Возвращаемый тип в сигнатуру не входит, но при override он должен быть совместимым.
- `@Override` защищает от случайной перегрузки: если сигнатура не совпала, компилятор сообщит об ошибке.

### Объяснение кода
- `NotificationSender` содержит `send(String)` и перегруженный `send(String, int)`.
- `EmailSender` и `ConsoleSender` переопределяют только `send(String)`.
- В `Main` есть ссылка `NotificationSender asBase = new EmailSender()`.
  - `asBase.send("hello")` вызывает `EmailSender.send`, потому что это override и работает dynamic dispatch.
  - `asBase.send("hello", 5)` вызывает `NotificationSender.send(String, int)`, потому что этот метод не переопределён в `EmailSender`.
- Если у наследника объявить `send(Object)` без `@Override`, это будет не override, а overload. Эта ловушка разобрана в задании 6.

**Подробнее по шагам.**
1. Компилятор видит `asBase.send("hello")`. В статическом типе `NotificationSender` есть `send(String)`, значит вызов корректен.
2. JVM смотрит на объект `EmailSender` и ищет в нём `send(String)`. Он там есть, поэтому вызывается реализация наследника.
3. Для `asBase.send("hello", 5)` компилятор ищет метод с двумя аргументами: `String` и `int`. В `NotificationSender` есть `send(String, int)`.
4. В `EmailSender` такого метода нет, поэтому вызывается унаследованный метод родителя.

**Главное отличие.** Override — это про замену реализации при одинаковой сигнатуре. Overload — это про выбор удобного метода по аргументам.

### Что могут спросить и как отвечать
**Чем override отличается от overload?**
Override — переопределение метода родителя с той же сигнатурой в наследнике, работает через dynamic dispatch. Overload — несколько методов с одним именем и разными параметрами, выбор происходит на этапе компиляции.

**Почему overload выбирается на этапе компиляции?**
Компилятор знает статический тип ссылки и типы аргументов и на этом основании выбирает подходящую сигнатуру. JVM уже получает готовую инструкцию вызова.

**Что будет, если в наследнике изменить тип параметра?**
Это будет новый перегруженный метод, а не переопределение. При вызове через родительский тип сработает родительский метод, а не метод наследника.

**Зачем ставить `@Override`?**
Чтобы компилятор проверил, что метод действительно переопределяет родительский. Если сигнатура не совпала, ошибка проявится сразу при компиляции, а не в runtime.

### Построчный разбор кода

Ключевые файлы: `NotificationSender.java`, `EmailSender.java`, `ConsoleSender.java`, `Main.java`.

```java
public class NotificationSender {                              // 1
    public void send(String message) { ... }                   // 2
    public void send(String message, int priority) { ... }     // 3
}                                                              // 4

public class EmailSender extends NotificationSender {           // 5
    @Override                                                  // 6
    public void send(String message) { ... }                   // 7
}                                                              // 8

NotificationSender asBase = new EmailSender();                 // 9
EmailSender asEmail = new EmailSender();                       // 10
asBase.send("hello");                                          // 11
asEmail.send("hello");                                         // 12
asBase.send("hello", 5);                                       // 13
asEmail.send("hello", 5);                                      // 14
```

1. `NotificationSender` — базовый класс с двумя методами отправки.
2. `send(String)` — метод, который наследники будут переопределять; для `String` это override.
3. `send(String, int)` — перегрузка: другое имя параметров, тот же метод по имени, но другая сигнатура.
4. `}` — закрывает базовый класс.
5. `EmailSender extends NotificationSender` — наследник получает оба метода родителя.
6. `@Override` — компилятор проверяет, что ниже действительно переопределяется метод родителя.
7. `send(String)` в наследнике — same signature, поэтому это override, а не overload.
8. `}` — закрывает наследника.
9. `asBase` — статический тип `NotificationSender`, динамический тип `EmailSender`.
10. `asEmail` — статический и динамический тип совпадают: `EmailSender`.
11. `asBase.send("hello")` — override: JVM смотрит на объект `EmailSender` и вызывает его `send(String)`.
12. `asEmail.send("hello")` — тот же метод наследника, результат такой же.
13. `asBase.send("hello", 5)` — overload: компилятор видит `send(String, int)` в `NotificationSender`; в `EmailSender` такого метода нет, вызывается родительский.
14. `asEmail.send("hello", 5)` — снова вызывается унаследованный `send(String, int)`: перегрузка выбирается по статическому типу и аргументам.

## Задание 3. Полиморфный массив

### Условие
Сложить разные реализации одного интерфейса в массив интерфейсного типа и обойти его без `if`/`instanceof` по типу. Показать, что добавление новой реализации не меняет код обхода.

### Теория
- Массив можно объявить типом интерфейса: `CourseFormatter[]`.
- В такой массив можно положить объекты любого класса, реализующего этот интерфейс.
- При обходе вызывается метод интерфейса, а JVM выбирает нужную реализацию по динамическому типу.
- **Полиморфизм** позволяет писать клиентский код один раз и не добавлять `switch`/`if` под каждый конкретный класс.
- Это пример принципа **Open/Closed**: код открыт для расширения новыми классами, но закрыт для изменения при добавлении реализации.

### Объяснение кода
- `JsonCourseFormatter` реализует `CourseFormatter` из `task01` и возвращает JSON-подобную строку.
- В `Main` создаётся массив из `CompactCourseFormatter`, `DetailedCourseFormatter` и `JsonCourseFormatter`.
- Обход идёт через `for-each`, внутри вызывается только `formatter.format(course)`.
- Нет проверок `if (formatter instanceof ...)`: поведение инкапсулировано в самих реализациях.
- Чтобы добавить четвёртый формат, достаточно создать новый класс и добавить его объект в массив; цикл менять не нужно.

**Подробнее по шагам.**
1. `CourseFormatter[] formatters = { ... }` — массив хранит ссылки типа интерфейса.
2. В каждой ячейке лежит объект конкретного класса, но для клиента все элементы имеют тип `CourseFormatter`.
3. В цикле `for (CourseFormatter formatter : formatters)` переменная `formatter` на каждом шаге ссылается на новый объект.
4. Вызов `formatter.format(course)` одинаковый, но JVM каждый раз выбирает реализацию по фактическому классу.
5. Новый класс `JsonCourseFormatter` просто добавляется в массив, и цикл начинает его обрабатывать без изменений.

**Почему это полиморфный массив.** Потому что элементы массива имеют общий тип, но разные динамические классы и разное поведение.

### Что могут спросить и как отвечать
**Что такое полиморфизм?**
Это способность одного вызова работать с объектами разных классов через общий тип. В задании один вызов `formatter.format(course)` даёт разный результат для компактного, подробного и JSON-форматтера.

**Почему массив называется полиморфным?**
Он объявлен как массив интерфейса, но хранит объекты разных реализаций. Один и тот же обход вызывает разные реализации метода.

**Почему здесь не нужен `instanceof`?**
Потому что каждая реализация сама знает, как форматировать курс. Клиенту не нужно проверять тип: он работает через общий контракт.

**Что изменится при добавлении новой реализации?**
Нужно создать новый класс, реализовать `format` и добавить объект в массив. Код обхода и клиентская логика не меняются.

**В чём здесь проявляется Open/Closed?**
Код открыт для расширения: можно добавлять новые форматтеры. Но он закрыт для изменения: существующий цикл не нужно переписывать.

### Построчный разбор кода

Ключевой файл: `java1/task03/Main.java`. Здесь важен именно обход массива, а не устройства форматтеров.

```java

    new CompactCourseFormatter(),                 // 2
    new DetailedCourseFormatter(),                // 3
    new JsonCourseFormatter()                     // 4
};                                                // 5

for (CourseFormatter formatter : formatters) {    // 6
    System.out.println(formatter.format(course)); // 7
}                                                 // 8
```

1. `CourseFormatter[]` — массив интерфейсного типа; в нём могут лежать любые реализации контракта.
2. `new CompactCourseFormatter()` — первая реализация, компилятор видит её как `CourseFormatter`.
3. `new DetailedCourseFormatter()` — вторая реализация в том же массиве.
4. `new JsonCourseFormatter()` — третья реализация; массив не меняется при добавлении новых классов.
5. `};` — массив создан; конкретные типы элементов стёрты до общего типа `CourseFormatter`.
6. `for (CourseFormatter formatter : formatters)` — обход не знает конкретных классов, работает только с контрактом.
7. `formatter.format(course)` — dynamic dispatch: на каждой итерации JVM вызывает реализацию фактического объекта.
8. `}` — конец цикла; код обхода не содержит `if`/`instanceof` по типу.

## Задание 4. Абстрактный базовый класс и шаблонный метод

### Условие
Вынести общий алгоритм отправки сообщения в абстрактный базовый класс, а различающуюся часть — в абстрактный метод. Запретить наследникам менять общий алгоритм.

### Теория
- **Абстрактный класс** может содержать и готовый код, и абстрактные методы.
- **Абстрактный метод** не имеет тела и обязан быть реализован в наследниках.
- **Шаблонный метод** — это метод, который задаёт общий скелет алгоритма и вызывает абстрактные шаги.
- `final` запрещает переопределение метода, чтобы наследник не сломал общий алгоритм.
- **Инвариант** — правило, которое должно выполняться всегда. Здесь это проверка адресата и порядок шагов.

### Объяснение кода
- `AbstractNotificationSender` хранит `private final String recipient`.
- `send(String)` объявлен `public final`: он проверяет адресата, печатает начало отправки, вызывает `doSend`, затем печатает завершение.
- `doSend(String)` объявлен `protected abstract` — это точка расширения.
- `EmailSender` и `ConsoleSender` реализуют только `doSend`, а общий порядок шагов остаётся в родителе.
- Если адресат `null` или состоит из пробелов, выводится ошибка и `doSend` не вызывается.
- Создать `new AbstractNotificationSender(...)` нельзя: класс абстрактный.

**Подробнее по шагам.**
1. `send` сначала проверяет `recipient == null || recipient.isBlank()`. Это общая проверка для всех каналов.
2. Если адресат пустой, метод печатает ошибку и завершается, не вызывая `doSend`.
3. Если адресат корректный, печатается начало отправки.
4. Вызывается `doSend(message)` — здесь срабатывает реализация наследника.
5. После возврата из `doSend` печатается завершение. Наследник не может пропустить этот шаг, потому что `send` объявлен `final`.

**Почему `final` важен.** Без `final` наследник мог бы переопределить `send` и, например, не проверять адресата или не печатать завершение. `final` защищает общий контракт алгоритма.

**Почему абстрактный класс, а не интерфейс.** Здесь есть общее состояние (`recipient`) и общий код (проверка и обрамление), поэтому абстрактный класс подходит лучше.

### Что могут спросить и как отвечать
**Что такое абстрактный класс?**
Это класс, от которого нельзя создать объект напрямую. Он может содержать готовые методы и абстрактные методы, которые обязаны реализовать наследники.

**Что такое шаблонный метод?**
Это метод, который задаёт общий порядок шагов алгоритма, а часть шагов выносит в абстрактные методы. Здесь шаблонный метод — `send`.

**Почему `send` сделан `final`?**
Чтобы наследники не могли изменить общий алгоритм: проверку адресата, порядок шагов и завершение. Они могут менять только `doSend`.

**Что будет, если убрать `final`?**
Наследник сможет переопределить `send` и сломать инвариант, например пропустить проверку адресата.

**Зачем нужен абстрактный `doSend`?**
Это точка расширения: каждый канал отправки реализует только свою специфику, а общий код не дублируется.

**Почему нельзя создать объект абстрактного класса?**
Потому что у него могут быть абстрактные методы без реализации. Компилятор запрещает создание такого объекта.

### Построчный разбор кода

Ключевые файлы: `AbstractNotificationSender.java`, `EmailSender.java`, `ConsoleSender.java`.

```java
public abstract class AbstractNotificationSender {                  // 1
    private final String recipient;                                 // 2

    protected AbstractNotificationSender(String recipient) {        // 3
        this.recipient = recipient;                                 // 4
    }                                                               // 5

    public final void send(String message) {                        // 6
        if (recipient == null || recipient.isBlank()) {             // 7
            System.out.println("ERR: recipient is empty");          // 8
            return;                                                 // 9

        System.out.println("Sending to " + recipient + "...");      // 11
        doSend(message);                                            // 12

    protected abstract void doSend(String message);                 // 15
}                                                                   // 16
```

13. Печать завершения — общий шаг, который выполняется после конкретной отправки.
14. `}` — конец `send`.
15. `protected abstract void doSend(...)` — наследник обязан реализовать именно этот шаг.
16. `}` — конец абстрактного класса.
17. `EmailSender` — конкретный наследник, который можно создать через `new`.

## Задание 5. Интерфейс или абстрактный класс

### Условие
Для пяти сущностей выбрать интерфейс или абстрактный класс, обосновать выбор и объяснить цену альтернативы. Кода нет, ответ письменный.

### Теория
- **Интерфейс** выбирают, когда нужен контракт/роль без общего состояния. Класс может реализовать много интерфейсов.
- **Абстрактный класс** выбирают, когда есть общее состояние и общий код, а отношение — «является». В Java можно наследовать только один класс.
- Неправильный выбор приводит к дублированию кода, потере полиморфизма или невозможности наследовать другой класс.
- **Композиция** часто лучше наследования: объект содержит зависимость, а не наследует её поведение.

### Объяснение кода
В `Answers1.md` разобраны пять сущностей:

| Сущность | Решение | Причина |
|---|---|---|
| `Identifiable` | интерфейс | Контракт «умею возвращать id», общего состояния нет. |
| `CoursePolicy` | интерфейс | Поведение-стратегия, несколько независимых реализаций. |
| `BaseEntity` | абстрактный класс | Общие поля `id`, `createdAt` и общий код, отношение «является». |
| `Formatter<T>` | интерфейс | Контракт преобразования в строку, реализации не связаны иерархией. |
| `ClockProvider` | интерфейс | Позволяет подменять источник времени и делать тесты детерминированными. |

- Если сделать `BaseEntity` интерфейсом, придётся дублировать общее состояние `id` и `createdAt` в каждом классе.
- Если сделать `Identifiable` абстрактным классом, наследники потеряют возможность наследовать другой класс из-за одиночного наследования.
- Для `ClockProvider` интерфейс важен для тестируемости: можно подставить фиксированное время вместо `Instant.now()`.

**Подробнее по каждой сущности.**
1. `Identifiable` — это роль, а не сущность. Разные и несвязанные классы могут иметь `id`, поэтому интерфейс.
2. `CoursePolicy` — алгоритм проверки. Реализаций несколько, они не связаны общим состоянием, поэтому интерфейс и паттерн «Стратегия».
3. `BaseEntity` — базовая сущность с общим состоянием и общими методами. Наследование здесь оправдано, но класс должен быть абстрактным, чтобы нельзя было создать бессмысленный `new BaseEntity()`.
4. `Formatter<T>` — контракт «преобразовать значение в строку». Форматов может быть много, они не связаны иерархией, поэтому интерфейс.
5. `ClockProvider` — источник времени. В тестах нужно подменять реальное время фиксированным, поэтому интерфейс.

### Что могут спросить и как отвечать
**Когда выбирать интерфейс, а когда абстрактный класс?**
Интерфейс — когда нужен только контракт или роль без общего состояния. Абстрактный класс — когда есть общее состояние и общий код, а также осмысленное отношение «является».

**Что такое множественное наследование интерфейсов?**
Класс может реализовать несколько интерфейсов одновременно. Это позволяет совмещать разные роли, например `Readable` и `Writable`. Если два интерфейса дают конфликтующие `default`-методы, класс обязан явно разрешить конфликт.

**Почему `BaseEntity` не интерфейс?**
Потому что у него есть общее состояние `id` и `createdAt` и общий код. В интерфейсе нельзя удобно хранить такое состояние, и его пришлось бы дублировать.

**Зачем `ClockProvider`, если есть `Instant.now()`?**
Чтобы не зависеть от реального времени. В тестах можно подставить фиксированное время и получить воспроизводимый результат.

**Что будет, если `Identifiable` сделать абстрактным классом?**
Классы, которые уже наследуют что-то другое, не смогут стать `Identifiable`, потому что в Java только одно наследование классов.

## Задание 6. Переопределение без случайной перегрузки

### Условие
Показать ловушку: метод наследника с другим типом параметра является перегрузкой, а не переопределением. Затем показать корректное переопределение с `@Override`.

### Теория
- Для override нужна **одинаковая сигнатура**: имя, параметры и совместимый возвращаемый тип.
- Если параметр отличается, это overload. Компилятор не считает такой метод переопределением.
- `@Override` заставляет компилятор проверить, что метод действительно переопределяет родительский.
- Нельзя сужать доступ: если в родителе `public`, в наследнике нельзя сделать `protected`.
- Возвращаемый тип при override может быть ковариантным: например, `String` вместо `Object`, но не наоборот.

### Объяснение кода
- `BrokenSender` содержит `public String send(String message)`.
- `BrokenEmailSender` объявляет `public String send(Object message)` без `@Override`. Это перегрузка, а не override.
- Если вызвать `broken.send("hello")` через тип `BrokenSender`, сработает родительский `send(String)`, потому что в наследнике нет именно `send(String)`.
- Чтобы вызвать `send(Object)`, нужен статический тип `BrokenEmailSender` и аргумент типа `Object`.
- В `FixedSender`/`FixedEmailSender` сигнатура совпадает, стоит `@Override`, поэтому вызывается реализация наследника.
- В `BrokenMethods.txt` дополнительно показаны ошибки сужения доступа и несовместимого возвращаемого типа.
- Точные сообщения компилятора: для `public` → `protected` — `attempting to assign weaker access privileges; was public`; для `Object` вместо `String` — `return type Object is not compatible with String`.

**Подробнее по шагам.**
1. В `BrokenSender` метод `send(String)` объявлен как `public`.
2. В `BrokenEmailSender` программист пишет `send(Object)` и думает, что переопределил метод. Но типы параметров разные, значит это новый overload.
3. При вызове через `BrokenSender` компилятор видит только `send(String)` и связывает вызов с родителем.
4. Даже если объект имеет тип `BrokenEmailSender`, в нём нет `send(String)`, поэтому dynamic dispatch не находит реализацию наследника.
5. В исправленной версии `FixedEmailSender.send(String)` совпадает по сигнатуре и помечен `@Override`, поэтому вызов через `FixedSender` попадает в наследника.

**Почему `@Override` помогает.** Если бы в `BrokenEmailSender` стоял `@Override` над `send(Object)`, компилятор сразу сказал бы, что такой метод не переопределяет родительский. Ошибка была бы найдена на этапе компиляции.

### Что могут спросить и как отвечать
**Почему сломанный вариант компилируется?**
Потому что `send(Object)` — допустимый перегруженный метод. Компилятор не знает, что программист хотел переопределить `send(String)`, если нет `@Override`.

**Чем `send(Object)` отличается от `send(String)`?**
Это разные сигнатуры. `send(String)` принимает только строку, `send(Object)` — любой объект. Для override нужна именно одинаковая сигнатура.

**Как `@Override` помогает найти ошибку?**
Он требует, чтобы метод действительно переопределял метод родителя. Если сигнатура не совпадает, компилятор выдаёт ошибку.

**Можно ли в наследнике сузить `public` до `protected`?**
Нет. Нельзя уменьшать видимость переопределяемого метода, иначе клиент через родительский тип потеряет доступ к методу.

**Можно ли изменить возвращаемый тип?**
Можно только на совместимый более конкретный тип (ковариантный возврат). Например, `String` вместо `Object` допустимо, а `Object` вместо `String` — нет.

## Задание 7. Композиция вместо наследования: декораторы

### Условие
Показать, что добавление логирования, retry и метрик через наследование приводит к комбинаторному взрыву. Заменить это композицией декораторов.

### Теория
- **Наследование** жёстко фиксирует поведение на этапе компиляции. Для каждого сочетания функций нужен отдельный класс.
- **Композиция** позволяет собрать объект из обёрток: каждая обёртка реализует тот же интерфейс и хранит внутри другой объект.
- **Декоратор** добавляет поведение до/после делегирования, не меняя исходный класс.
- **Делегирование** — передача работы внутреннему объекту через `inner.send(message)`.
- Порядок обёрток влияет на результат.

### Объяснение кода
- `NotificationSender` — интерфейс с `send(String)`. У него один абстрактный метод, поэтому его можно заменить лямбдой.
- `EmailSender` и `ConsoleSender` — базовые реализации.
- `LoggingEmailSender extends EmailSender` — старый вариант логирования через наследование.
- `LoggingSender`, `RetrySender`, `MetricsSender`, `FlakySender` реализуют `NotificationSender` и хранят `inner`.
  - `LoggingSender` печатает `LOG before`, вызывает `inner.send`, в `finally` печатает `LOG after`.
  - `RetrySender` делает несколько попыток, ловит `RuntimeException`; если все попытки неудачны, бросает `IllegalStateException` с причиной.
  - `MetricsSender` считает количество вызовов.
  - `FlakySender` имитирует временные сбои.
- В `Main` показаны цепочки `Logging(Retry(Flaky(Email)))`, `Retry(Logging(Flaky(Email)))` и `Metrics(Logging(Email))`.
- Если `LoggingSender` стоит снаружи retry, логируется один вызов. Если внутри retry, логируется каждая попытка.

**Подробнее по шагам.**
1. Клиент вызывает `send` у самой внешней обёртки.
2. Внешняя обёртка выполняет своё дополнительное действие, затем вызывает `inner.send`.
3. Внутренняя обёртка делает то же самое и передаёт вызов глубже, пока дело не дойдёт до реального `EmailSender`.
4. После возврата управление идёт обратно по цепочке, и каждая обёртка может выполнить код после вызова.
5. Поэтому порядок вложения определяет, когда именно сработает логирование, retry или подсчёт метрик.

**Почему наследование плохо в этом примере.** Для двух-трёх независимых функций количество подклассов растёт как комбинация вариантов: нужен класс для логирования, отдельный для retry, отдельный для логирования с retry и т.д. Декораторы дают по одному классу на функцию и позволяют собирать цепочки в runtime.

### Что могут спросить и как отвечать
**Что такое композиция?**
Это когда объект содержит другой объект и использует его для выполнения части работы, вместо того чтобы наследовать его поведение.

**Почему композиция лучше наследования в этом примере?**
Она позволяет добавлять функции независимо и комбинировать их в любом порядке. Не нужно создавать отдельный класс под каждое сочетание логирования, retry и метрик.

**Как работает декоратор?**
Декоратор реализует тот же интерфейс, что и оборачиваемый объект, хранит его внутри и добавляет поведение до или после делегирования.

**Почему порядок обёрток важен?**
Потому что каждая обёртка решает, когда вызвать внутреннюю. Например, логирование снаружи retry даст один лог, а внутри retry — лог на каждую попытку.

**Где здесь `try/finally` и зачем он нужен?**
В `LoggingSender` `finally` гарантирует, что запись `LOG after` будет выполнена даже при исключении во внутреннем вызове.

### Построчный разбор кода

Ключевые файлы: `RetrySender.java`, `LoggingSender.java`, `Main.java`. Показываю главный декоратор и порядок обёртывания.

```java

    private final NotificationSender inner;                       // 2
    private final int attempts;                                   // 3

    public RetrySender(NotificationSender inner, int attempts) {  // 4
        this.inner = inner;                                       // 5
        this.attempts = attempts;                                 // 6
    }                                                             // 7

    @Override                                                     // 8
    public void send(String message) {                            // 9
        RuntimeException lastError = null;                        // 10
        for (int i = 1; i <= attempts; i++) {                     // 11
            try {                                                 // 12
                System.out.println("RETRY attempt " + i);         // 13
                inner.send(message);                              // 14
                return;                                           // 15
            } catch (RuntimeException e) {                        // 16
                lastError = e;                                    // 17
            }                                                     // 18
        }                                                         // 19
        throw new IllegalStateException("all attempts failed", lastError); // 20
    }                                                             // 21
}                                                                 // 22

NotificationSender order1 = new LoggingSender(                    // 23
    new RetrySender(new FlakySender(email, 1), 3)                 // 24
);                                                                // 25
order1.send("hello");                                             // 26
```

1. `implements NotificationSender` — декоратор сам является отправителем, поэтому его можно подставить вместо реального.
2. `inner` — обёрнутый отправитель; декоратор не наследует его класс, а содержит объект.
3. `attempts` — сколько раз разрешено повторить отправку.
4. Конструктор принимает внутренний отправитель и количество попыток.
5. `this.inner = inner` — сохраняет ссылку на обёрнутый объект.
6. `this.attempts = attempts` — сохраняет лимит попыток.
7. `}` — конец конструктора.
8. `@Override` — реализуем метод интерфейса.
9. `send` — вся дополнительная логика (повторы) находится здесь, а не в `EmailSender`.
10. `lastError` — хранит последнюю ошибку, чтобы потом приложить её как cause.
11. Цикл от 1 до `attempts` — каждая итерация это одна попытка.
12. `try` — попытка может закончиться ошибкой.
13. Печать номера попытки помогает увидеть порядок работы.
14. `inner.send(message)` — реальная отправка через обёрнутый объект.
15. `return` — если отправка прошла, повторять больше не нужно.
16. `catch (RuntimeException e)` — ловим ошибку конкретного семейства, чтобы повторить попытку.
17. `lastError = e` — запоминаем причину последнего сбоя.
18. `}` — конец обработки ошибки.
19. `}` — конец цикла; если все попытки упали, идём дальше.
20. `throw new IllegalStateException(..., lastError)` — сообщаем, что все попытки исчерпаны, сохраняя причину.
21. `}` — конец `send`.
22. `}` — конец декоратора.
23. `new LoggingSender(...)` — внешний декоратор логирования.
24. `new RetrySender(new FlakySender(email, 1), 3)` — внутри логирования лежит повтор, а внутри повтора — нестабильный отправитель.
25. `)` — завершение конструкции; порядок обёртывания определяет порядок поведения.

## Задание 8. Нарушение LSP и разделение интерфейсов

### Условие
Показать нарушение принципа подстановки Лисков: read-only репозиторий вынужден бросать исключение в `save`. Исправить через разделение контрактов на чтение и запись.

### Теория
- **LSP (Liskov Substitution Principle):** объект наследника должен использоваться там же, где объект родителя, без неожиданных ошибок.
- Если наследник бросает `UnsupportedOperationException` на обещанный родителем метод, это нарушение LSP.
- **Interface Segregation:** лучше несколько маленьких интерфейсов, чем один «толстый» с лишними методами.
- Разделение интерфейсов переносит ошибку из runtime в compile time.
- **Optional** помогает явно показать, что значения может не быть.

### Объяснение кода
- Сломанная иерархия: `CourseRepository` с `save` и `findById`; `BrokenReadOnlyCourseRepository` наследует её и бросает исключение в `save`.
- Исправленная модель:
  - `ReadableCourseRepository` — только `findById`;
  - `WritableCourseRepository` — только `save`;
  - `FullCourseRepository extends ReadableCourseRepository, WritableCourseRepository`.
- `ReadOnlyCourseRepository` реализует только чтение и не обещает `save`.
- `InMemoryCourseRepository` реализует оба контракта.
- В `Main` клиенты `printCourse(ReadableCourseRepository, ...)` и `addCourse(WritableCourseRepository, ...)` принимают только нужные возможности.
- `findById` возвращает `Optional<Course>`, а не `null`.

**Подробнее по шагам.**
1. В старом варианте клиент получает `CourseRepository` и думает, что может вызвать `save`.
2. Если реально это `BrokenReadOnlyCourseRepository`, `save` бросает `UnsupportedOperationException`. Клиент не ожидал такого поведения — LSP нарушен.
3. В новой модели read-only репозиторий вообще не реализует `WritableCourseRepository`.
4. Поэтому его нельзя передать в `addCourse(WritableCourseRepository, ...)` — это ошибка компиляции, а не runtime-сюрприз.
5. `FullCourseRepository` объединяет оба узких интерфейса и подходит для мест, где нужны и чтение, и запись.

**Почему это лучше.** Клиент получает только те возможности, которые ему действительно нужны. Ошибка использования видна при компиляции.

### Что могут спросить и как отвечать
**Что такое LSP?**
Принцип подстановки Лисков: наследник должен заменять родителя без изменения корректности программы. Если клиент ждёт работающий `save`, наследник не должен бросать на этом методе исключение.

**Почему `UnsupportedOperationException` в наследнике — плохо?**
Потому что родитель обещает метод, а наследник его не выполняет. Клиент, работающий через родительский тип, получает неожиданную ошибку в runtime.

**Как разделение интерфейсов решает проблему?**
Read-only репозиторий просто не реализует интерфейс записи, поэтому его нельзя использовать там, где нужна запись. Ошибка обнаруживается компилятором.

**Почему `Optional` лучше `null`?**
`Optional` явно говорит, что результата может не быть, и заставляет клиента обработать этот случай. `null` легко забыть проверить, что приводит к `NullPointerException`.

**Что такое Interface Segregation?**
Принцип разделения интерфейсов: клиент не должен зависеть от методов, которые ему не нужны. Лучше несколько узких интерфейсов, чем один большой.

### Построчный разбор кода

Ключевые файлы: `ReadableCourseRepository.java`, `WritableCourseRepository.java`, `FullCourseRepository.java`, `BrokenReadOnlyCourseRepository.java`, `Main.java`.

```java

}                                                        // 3

public interface WritableCourseRepository {              // 4
    void save(Course course);                            // 5

public interface FullCourseRepository                    // 7
        extends ReadableCourseRepository, WritableCourseRepository { // 8
}                                                        // 9

public class BrokenReadOnlyCourseRepository              // 10
        extends CourseRepository {                       // 11
```

1. `ReadableCourseRepository` — отдельный контракт только на чтение; он ничего не обещает про запись.

3. `}` — клиенту чтения больше ничего не нужно.
4. `WritableCourseRepository` — отдельный контракт только на запись.

15. `}` — конец метода.
16. `}` — конец класса; правильное решение — не наследовать `save`, а разделить интерфейсы.
17. `printCourse(readOnly, 1)` — клиенту чтения достаточно `ReadableCourseRepository`.
18. `addCourse(full, ...)` — клиенту записи нужен `WritableCourseRepository`; read-only объект сюда не попадёт уже на этапе компиляции.

## Задание 9. Политика допуска как стратегия

### Условие
Вынести алгоритм допуска студента на курс в отдельный объект-политику. Служба зачисления должна принимать политику извне и не зависеть от конкретной реализации.

### Теория
- **Стратегия** — паттерн, при котором алгоритм вынесен в отдельный объект и может подменяться.
- **Внедрение зависимости через конструктор** позволяет передать нужную реализацию снаружи.
- Сервис зависит только от интерфейса, поэтому новая политика не требует изменения сервиса.
- Политика может быть stateless (`AgePolicy`) или stateful (`CapacityPolicy`).
- **Open/Closed:** сервис закрыт для изменения, но открыт для расширения новыми политиками.

### Объяснение кода
- `EnrollmentPolicy` — интерфейс с `boolean canEnroll(Student student, Course course)`.
- `AgePolicy` проверяет минимальный возраст.
- `PrerequisitePolicy` проверяет, что студент прошёл нужный курс.
- `CapacityPolicy` хранит `capacity` и `enrolled`, проверяет наличие мест; `enrollOne()` увеличивает счётчик.
- `EnrollmentService` хранит `private final EnrollmentPolicy policy`, полученную через конструктор.
- `enroll` вызывает `policy.canEnroll`, печатает `Accepted`/`Rejected` и возвращает `boolean`.
- Важно: сервис сам не вызывает `enrollOne`; в `Main` и тестах счётчик увеличивается после успешного зачисления.

**Подробнее по шагам.**
1. Создаётся конкретная политика, например `new AgePolicy(18)`.
2. Она передаётся в `new EnrollmentService(policy)`.
3. Внутри сервиса хранится только ссылка типа `EnrollmentPolicy`.
4. При `enroll` сервис вызывает `policy.canEnroll(student, course)` и не знает, какая именно реализация внутри.
5. Если завтра появится `CountryPolicy` или `PaymentPolicy`, достаточно создать новый класс, реализующий `EnrollmentPolicy`, и передать его в сервис. Код сервиса не меняется.

**Почему `CapacityPolicy` особенная.** Она хранит состояние: сколько мест уже занято. Поэтому после успешного зачисления нужно вручную вызвать `enrollOne()`. Сервис этого не делает, чтобы не смешивать проверку политики и изменение её состояния.

### Что могут спросить и как отвечать
**Что такое паттерн «Стратегия»?**
Это способ вынести алгоритм в отдельный объект с общим интерфейсом и подменять его без изменения клиента. Здесь стратегии — разные политики допуска.

**Почему это стратегия, а не просто набор `if`?**
Потому что каждая политика — отдельный класс с общим контрактом. Клиент не выбирает поведение через `if`, а вызывает полиморфный метод `canEnroll`.

**Что даёт внедрение зависимости через конструктор?**
Сервис не создаёт политику сам, а получает её извне. Это позволяет подставлять разные реализации и тестировать сервис с простыми лямбдами.

**Почему `EnrollmentService` не знает о конкретной политике?**
Он зависит только от интерфейса `EnrollmentPolicy`. Это снижает связанность и позволяет добавлять новые политики без изменения сервиса.

**Как добавить новую политику без изменения сервиса?**
Создать класс, реализующий `EnrollmentPolicy`, и передать его в конструктор сервиса. Сервис менять не нужно.

### Построчный разбор кода

Ключевые файлы: `EnrollmentPolicy.java`, `EnrollmentService.java`, `AgePolicy.java`, `CapacityPolicy.java`, `PrerequisitePolicy.java`.

```java

}                                                          // 3
```

1. `EnrollmentPolicy` — контракт стратегии: можно ли зачислить студента.

3. `}` — сервис не знает, какие именно правила реализуют этот интерфейс.

6. Конструктор принимает любую реализацию `EnrollmentPolicy`.
7. `this.policy = policy` — сохраняет стратегию для вызовов `enroll`.
8. `}` — конец конструктора.
9. `enroll` — общий сценарий зачисления, не зависящий от конкретного правила.
10. `policy.canEnroll(...)` — dynamic dispatch вызывает правило, переданное в сервис.

13. `return true` — политика разрешила зачисление.
14. `}` — конец `enroll`.
15. `}` — конец сервиса.
16. `AgePolicy` — конкретная стратегия по возрасту.
17. `minAge` — параметр правила, задаётся при создании.
18. Конструктор сохраняет минимальный возраст.
19. `@Override` — реализуем метод интерфейса.
20. `canEnroll` — правило возраста.
21. `student.age() >= minAge` — единственное условие: возраст не меньше минимума.

## Задание 10. Конфликт default-методов

### Условие
Два интерфейса содержат `default`-метод с одинаковой сигнатурой. Класс, реализующий оба интерфейса, должен явно разрешить конфликт. Показать три способа разрешения.

### Теория
- `default`-метод в интерфейсе имеет готовую реализацию.
- Если класс реализует два интерфейса с одинаковым `default`-методом и не переопределяет его, компилятор выдаёт ошибку «unrelated defaults».
- Конфликт разрешается явным переопределением.
- Можно вызвать конкретную реализацию через `InterfaceName.super.method()`.
- Это пример множественного наследования поведения через интерфейсы.

### Объяснение кода
- `Notifier` и `Logger` оба содержат `default String describe()`.
- `FixedBoth` переопределяет `describe` и возвращает `Notifier.super.describe()`.
- `CombinedBoth` объединяет обе реализации: `Notifier.super.describe() + "+" + Logger.super.describe()`.
- `CustomBoth` возвращает собственное значение `"Custom"` и не использует default-реализации.
- `BrokenBoth.txt` специально не компилируется: класс реализует оба интерфейса, но не разрешает конфликт.
- Компилятор выдаёт: `error: class BrokenBoth inherits unrelated defaults for describe() from types Notifier and Logger`.
- В `Main` показаны результаты всех трёх корректных вариантов.

**Подробнее по шагам.**
1. Класс `FixedBoth implements Notifier, Logger` получает два `default`-метода `describe()` с одинаковой сигнатурой.
2. Компилятор не может выбрать, какой из них использовать, поэтому без переопределения класс не компилируется.
3. `FixedBoth` переопределяет `describe` и явно вызывает `Notifier.super.describe()`.
4. `CombinedBoth` вызывает оба варианта и объединяет результаты.
5. `CustomBoth` полностью игнорирует default-реализации и возвращает своё значение.

**Почему `BrokenBoth.txt` вынесен в отдельный файл.** Если бы он был в исходниках, весь проект не компилировался бы. Поэтому он хранится как текст для демонстрации ошибки.

### Что могут спросить и как отвечать
**Что такое `default`-метод?**
Это метод интерфейса с готовой реализацией. Класс может его не переопределять и использовать реализацию по умолчанию.

**Почему компилятор не выбирает default автоматически?**
Потому что оба интерфейса равноправны и компилятор не знает, какой вариант правильный. Java требует, чтобы программист явно разрешил конфликт.

**Как вызвать реализацию конкретного интерфейса?**
Через синтаксис `Notifier.super.describe()` или `Logger.super.describe()`.

**Чем `default`-метод отличается от абстрактного?**
Абстрактный метод не имеет тела и должен быть реализован. `default`-метод имеет реализацию и может быть унаследован без переопределения.

**Что будет, если один метод default, а другой абстрактный?**
Абстрактный метод всё равно нужно реализовать в классе. Если сигнатуры совпадают, реализация класса удовлетворит оба интерфейса.

### Построчный разбор кода

Ключевые файлы: `Notifier.java`, `Logger.java`, `FixedBoth.java`, `CombinedBoth.java`, `CustomBoth.java`.

```java
public interface Notifier {                         // 1
    default String describe() { return "Notifier"; } // 2
}                                                   // 3

public interface Logger {                           // 4
    default String describe() { return "Logger"; }  // 5
}                                                   // 6

public class FixedBoth implements Notifier, Logger { // 7
    @Override                                       // 8
    public String describe() {                      // 9
        return Notifier.super.describe();           // 10
    }                                               // 11
}                                                   // 12

public class CombinedBoth implements Notifier, Logger { // 13
    @Override                                       // 14
    public String describe() {                      // 15
        return Notifier.super.describe()            // 16
            + "+" + Logger.super.describe();        // 17
    }                                               // 18
}                                                   // 19
```

1. `Notifier` — первый интерфейс с `default`-методом.
2. `default String describe()` — готовая реализация, которую наследник может не переопределять.
3. `}` — конец интерфейса.
4. `Logger` — второй интерфейс.
5. У него такой же `default describe()`, поэтому у класса возникает конфликт двух реализаций.
6. `}` — конец второго интерфейса.
7. `FixedBoth implements Notifier, Logger` — класс получает два конфликтующих `default`-метода.
8. `@Override` — компилятор требует, чтобы класс явно разрешил конфликт.
9. `describe` — собственная реализация класса.
10. `Notifier.super.describe()` — явно выбираем реализацию из `Notifier`; без этого компилятор не поймёт, какой `default` использовать.
11. `}` — конец метода.
12. `}` — конец класса.
13. `CombinedBoth` — второй вариант разрешения конфликта.
14. `@Override` — снова обязательное переопределение.
15. `describe` — своя реализация.
16. `Notifier.super.describe()` — берём первую часть поведения.
17. `"+" + Logger.super.describe()` — добавляем вторую часть; получаем комбинированный результат.
18. `}` — конец метода.
19. `}` — конец класса. Третий вариант — `CustomBoth` — просто возвращает `"Custom"` и игнорирует оба `default`.

## Задание 11. Равенство в иерархии: equals/hashCode

### Условие
Показать нарушение симметричности `equals` в наследовании `Point` → `ColoredPoint`. Затем исправить двумя способами: строгим сравнением классов и композицией.

### Теория
- Контракт `equals`: рефлексивность, симметричность, транзитивность, согласованность, `false` при сравнении с `null`.
- Если `a.equals(b)`, то `b.equals(a)` тоже должно быть `true`.
- `equals` и `hashCode` должны быть согласованы: равные объекты обязаны иметь одинаковый `hashCode`.
- `instanceof` допускает сравнение с наследниками, `getClass()` требует одинаковый класс.
- Композиция помогает избежать проблем наследования.
- `hashCode` нужен для коллекций на основе хэш-таблиц: `HashMap`, `HashSet`.

### Объяснение кода
- `Point.equals` использует `o instanceof Point`, поэтому `Point` с теми же координатами может быть равен `ColoredPoint`.
- `ColoredPoint.equals` требует `o instanceof ColoredPoint`, поэтому обратное сравнение даёт `false`.
- Получается асимметрия: `p.equals(cp) == true`, а `cp.equals(p) == false`.
- `PointStrict` и `ColoredPointStrict` сравнивают `getClass()`, поэтому точки разных классов не равны, симметрия восстановлена.
- `PointValue` — `final`-класс; `ColoredPointValue` содержит `PointValue` и цвет через композицию. Наследования нет, конфликта равенства нет.
- `hashCode` строится по тем же полям, которые участвуют в `equals`.

**Подробнее по шагам.**
1. `Point` содержит `x`, `y`. `ColoredPoint` наследует `Point` и добавляет `color`.
2. Когда `Point.equals` получает `ColoredPoint`, проверка `instanceof Point` проходит, потому что наследник является точкой. Поэтому `p.equals(cp)` может вернуть `true`.
3. Когда `ColoredPoint.equals` получает обычный `Point`, проверка `instanceof ColoredPoint` не проходит, поэтому возвращается `false`.
4. Это нарушает симметричность: одно и то же сравнение в разных направлениях даёт разный результат.
5. В строгом варианте `getClass()` требует, чтобы классы были одинаковыми, поэтому `PointStrict` и `ColoredPointStrict` никогда не равны друг другу.
6. В варианте с композицией `ColoredPointValue` не является наследником `PointValue`, а содержит его. Это разные типы, и сравнение между ними всегда `false`, зато внутри одного типа всё симметрично.

**Почему `final` помогает.** Если класс нельзя наследовать, никто не добавит новое поле и не сломает `equals`/`hashCode` неожиданным образом.

### Что могут спросить и как отвечать
**В чём нарушение симметричности?**
`p.equals(cp)` может быть `true`, а `cp.equals(p)` — `false`. По контракту `equals` оба направления должны совпадать.

**Чем `instanceof` отличается от `getClass()` в `equals`?**
`instanceof` разрешает сравнение с наследниками. `getClass()` требует одинаковый класс, поэтому наследники считаются разными типами.

**Зачем `hashCode`, если есть `equals`?**
Хэш-коллекции сначала сравнивают `hashCode`, а потом `equals`. Если равные объекты имеют разные `hashCode`, они могут потеряться в `HashSet` или `HashMap`.

**Почему композиция решает проблему?**
`ColoredPointValue` не наследует `PointValue`, поэтому нет ситуации, когда объект одновременно «является» родителем и добавляет новое состояние. Сравниваются только объекты одного типа.

**Какие правила есть у `equals`?**
Рефлексивность, симметричность, транзитивность, согласованность и корректная обработка `null`.

### Построчный разбор кода

Ключевые файлы: `Point.java`, `ColoredPoint.java`, `PointStrict.java`, `PointValue.java`, `ColoredPointValue.java`.

## Задание 12. Sealed-иерархия результата

### Условие
Смоделировать результат зачисления как `sealed`-иерархию с фиксированным набором вариантов и обрабатывать его исчерпывающим `switch` без `default`.

### Теория
- `sealed interface`/`sealed class` ограничивает круг наследников через `permits`.
- Наследники обычно объявляются `final`, чтобы иерархия оставалась закрытой.
- Для sealed-типов компилятор проверяет полноту `switch`: все варианты должны быть обработаны.
- Если добавить новый вариант и не обновить `switch`, компиляция упадёт — это защита от забытых случаев.
- Это пример «закрытой иерархии»: набор вариантов известен и не расширяется случайно.

### Объяснение кода
- `EnrollmentResult` объявлен как `sealed interface ... permits Accepted, Rejected, WaitListed, Pending`.
- `Accepted`, `Rejected`, `WaitListed`, `Pending` — `final`-реализации с нужными полями.
- `ResultPrinter.describe` использует `switch`-выражение по типам и не содержит `default`.
- В `Main` создаётся массив из четырёх результатов и каждый обрабатывается через `describe`.
- Фактически в иерархии четыре варианта, включая `Pending`; код является источником истины.

**Подробнее по шагам.**
1. `permits` перечисляет все допустимые реализации. Другие классы не могут реализовать `EnrollmentResult`.
2. Каждая реализация `final`, поэтому у неё тоже не может быть наследников.
3. В `ResultPrinter.describe` есть `case Accepted`, `case Rejected`, `case WaitListed`, `case Pending`.
4. Компилятор видит, что все четыре варианта покрыты, и разрешает `switch` без `default`.
5. Если добавить новый вариант в `permits` и забыть `case`, компилятор выдаст ошибку о неполном `switch`.

**Почему `default` здесь вреден.** Он бы скрыл новый вариант: код скомпилировался бы, но новый результат обрабатывался бы неправильно. Без `default` компилятор заставляет обновить все места обработки.

### Что могут спросить и как отвечать
**Что такое sealed-класс/интерфейс?**
Это тип, который явно ограничивает, какие классы могут его наследовать или реализовывать. Список наследников задаётся через `permits`.

**Зачем нужен `permits`?**
Он фиксирует допустимые реализации. Благодаря этому компилятор знает полный набор вариантов и может проверять полноту `switch`.

**Почему реализации `final`?**
Чтобы у них не появились собственные наследники и sealed-иерархия оставалась действительно закрытой.

**Почему `switch` без `default` безопасен?**
Потому что компилятор проверяет, что покрыты все допустимые варианты. Если появится новый, код не скомпилируется, пока его не обработают.

**Что будет при добавлении нового варианта?**
Нужно добавить его в `permits` и обновить все `switch` по этому типу. Компилятор укажет места, которые нужно исправить.

### Построчный разбор кода

Ключевые файлы: `EnrollmentResult.java`, `Accepted.java`, `Rejected.java`, `WaitListed.java`, `Pending.java`, `ResultPrinter.java`, `Main.java`.

```java
public sealed interface EnrollmentResult                 // 1
        permits Accepted, Rejected, WaitListed, Pending { // 2
}                                                        // 3

public final class Accepted implements EnrollmentResult { // 4
    private final long studentId;                         // 5
    private final long courseId;                          // 6
    public Accepted(long studentId, long courseId) {      // 7
        this.studentId = studentId;                       // 8
        this.courseId = courseId;                         // 9
    }                                                     // 10
}                                                         // 11

public static String describe(EnrollmentResult result) {  // 12
    return switch (result) {                              // 13
        case Accepted a -> "accepted: " + a.studentId();  // 14
        case Rejected r -> "rejected: " + r.reason();     // 15
        case WaitListed w -> "waitlisted: " + w.position(); // 16
        case Pending p -> "pending: " + p.studentId();    // 17
    };                                                    // 18
}                                                         // 19

EnrollmentResult[] results = {                            // 20
    new Accepted(1, 10),                                  // 21
    new Rejected(2, 10, "no seats"),                      // 22
    new WaitListed(3, 10, 1),                             // 23
    new Pending(4, 10)                                    // 24
};                                                        // 25
```

1. `sealed interface` — разрешает реализацию только перечисленным типам.
2. `permits ...` — фиксирует четыре допустимых варианта; `Pending` здесь тоже есть.
3. `}` — иерархия закрыта, случайных наследников быть не может.
4. `Accepted` — конкретный вариант успешного результата.
5. `studentId` — данные, нужные для успешного результата.
6. `courseId` — второй параметр результата.
7. Конструктор принимает идентификаторы.
8. Сохраняет студента.
9. Сохраняет курс.
10. `}` — конец конструктора.
11. `}` — конец `Accepted`; остальные варианты устроены аналогично, но с разными полями.
12. `describe` — единая функция обработки результата.
13. `switch (result)` — сопоставление с образцом по типу.
14. `case Accepted a` — извлекает `Accepted` и даёт доступ к его методам.
15. `case Rejected r` — обрабатывает отказ и читает причину.
16. `case WaitListed w` — обрабатывает лист ожидания и позицию.
17. `case Pending p` — обрабатывает новый вариант; без этой строки компилятор выдаст ошибку, потому что `switch` должен быть исчерпывающим.
18. `};` — конец `switch`; `default` не нужен, sealed-иерархия известна компилятору.
19. `}` — конец `describe`.
20. Массив результатов — демонстрация всех четырёх вариантов.
21. `Accepted` — успешное зачисление.
22. `Rejected` — отказ с причиной.
23. `WaitListed` — очередь с позицией.
24. `Pending` — заявка ещё рассматривается.
25. `};` — массив создан; общий цикл ниже обрабатывает его без знания конкретных классов.

## Задание 13. Удаление type code

### Условие
Показать «сломанный» вариант, где тип уведомления хранится строкой и обрабатывается `switch`. Заменить это полиморфизмом: общий интерфейс и отдельный класс на каждый тип.

### Теория
- **Type code** — хранение типа в виде строки/числа и выбор поведения через `switch`.
- При добавлении нового типа приходится менять существующий класс; забытая ветка приводит к ошибке в runtime.
- Полиморфизм переносит поведение в классы-реализации: клиент вызывает общий метод, а JVM выбирает нужную реализацию.
- Полиморфизм особенно полезен, когда варианты отличаются поведением, а не просто значением.
- Если варианты отличаются только данными (например, размер скидки), иногда достаточно `Map`/`enum`, а не отдельного класса на каждый вариант.

### Объяснение кода
- `BrokenNotification` хранит `String type` и в `send` делает `switch` по `"email"`, `"sms"`, `"push"`, `default`.
- При неизвестном типе печатается `Unknown type: ...`.
- В полиморфном варианте есть интерфейс `NotificationSender` и классы `EmailSender`, `SmsSender`, `PushSender`.
- Каждый класс хранит свой адрес/телефон/deviceId и реализует `send`.
- `Main` создаёт массив `NotificationSender[]` и обходит его без проверок типа.
- Добавление нового канала требует только нового класса; цикл отправки не меняется.

**Подробнее по шагам.**
1. В `BrokenNotification` один класс знает обо всех каналах и решает, что делать, через `switch`.
2. Если добавить `"telegram"`, нужно изменить `BrokenNotification` и добавить новую ветку.
3. Если забыть ветку, ошибка проявится только при отправке в runtime.
4. В полиморфном варианте каждый канал — отдельный класс. Он сам знает, как отправить сообщение.
5. Клиент работает с массивом `NotificationSender[]` и вызывает `send` у каждого элемента. JVM выбирает реализацию по фактическому классу.
6. Новый канал — это новый класс, существующий цикл и клиентский код не меняются.

**Граница применимости.** Если отличие только в числовом параметре, например скидка 10/20/30%, то делать три класса может быть избыточно. Тогда лучше `Map` или `enum`. Полиморфизм оправдан, когда меняется именно поведение.

### Что могут спросить и как отвечать
**Что такое type code?**
Это когда тип объекта хранится отдельным полем (строкой или числом), а поведение выбирается через `switch` или `if` по этому полю.

**Чем type code плох?**
Он нарушает Open/Closed: при добавлении нового типа нужно менять существующий класс. Кроме того, забытая ветка часто обнаруживается только в runtime.

**Когда `switch` по типу всё же допустим?**
Когда вариантов мало, они стабильны и отличаются только данными. Но если поведение разное и типы добавляются, лучше полиморфизм.

**Как добавить новый тип уведомления?**
В полиморфном варианте — создать новый класс, реализующий `NotificationSender`, и добавить его в массив. В type code пришлось бы менять `switch`.

**Где здесь dynamic dispatch?**
В вызове `sender.send(message)` для элемента массива: JVM выбирает реализацию по фактическому классу объекта.

### Построчный разбор кода

Ключевые файлы: `BrokenNotification.java`, `NotificationSender.java`, `EmailSender.java`, `SmsSender.java`, `PushSender.java`, `Main.java`.

```java

    private final String recipient;                       // 3

        switch (type) {                                   // 5

            case "sms": ... break;                        // 7
            case "push": ... break;                       // 8
            default: ...                                  // 9
        }                                                 // 10
    }                                                     // 11
}                                                         // 12

public interface NotificationSender {                     // 13
    void send(String message);                            // 14
}                                                         // 15

public class EmailSender implements NotificationSender {   // 16
    public void send(String message) { ... }              // 17
}                                                         // 18

NotificationSender[] senders = {                          // 19
    new EmailSender(...),                                 // 20
    new SmsSender(...),                                   // 21
```

1. `BrokenNotification` — один класс, который знает про все типы уведомлений.
2. `type` — строковый type code; по нему выбирается ветка.
3. `recipient` — получатель, общий для всех типов.
4. `send` — единый метод, внутри которого спрятан `switch`.
5. `switch (type)` — выбор поведения по строке; новые типы требуют правки этого класса.
6. `case "email"` — одна из веток; при добавлении push/sms нужно не забыть обновить switch.
7. `case "sms"` — ещё одна ветка, дублирующая логику отправки.
8. `case "push"` — третья ветка; класс разрастается.
9. `default` — обработка неизвестного типа; легко забыть добавить новый case.
10. `}` — конец switch.
11. `}` — конец `send`.
12. `}` — конец «сломанного» класса.
13. `NotificationSender` — контракт, который знает только про отправку.
14. `send` — конкретный способ выбирает реализация, а не клиент.
15. `}` — конец интерфейса.
16. `EmailSender` — отдельная реализация email.
17. `send` — знает только про email; не содержит switch по чужим типам.
18. `}` — конец реализации.
19. Массив интерфейсного типа хранит разные реализации.
20. `new EmailSender(...)` — email-отправитель.
21. `new SmsSender(...)` — sms-отправитель.
22. `new PushSender(...)` — push-отправитель.
23. `};` — массив готов; добавление нового типа не меняет цикл.
24. Обход массива работает только с контрактом.
25. `sender.send("hello")` — dynamic dispatch выбирает реализацию по фактическому объекту.
26. `}` — конец цикла; `switch` и type code больше не нужны.

## Задание 14. Наследование взрывает комбинации

### Условие
Есть две независимые оси: формат курса и политика оплаты. Показать, что наследование под каждую комбинацию даёт комбинаторный взрыв, а композиция позволяет свободно комбинировать варианты.

### Теория
- Если есть `n` форматов и `m` оплат, наследование потребует `n × m` классов под каждую комбинацию.
- Композиция требует `n + m` классов: формат и оплата становятся отдельными стратегиями.
- `CourseInfo` не наследует формат и оплату, а содержит их.
- Анонимные классы позволяют добавить новый вариант без создания отдельного именованного класса.
- **Композиция вместо наследования** — принцип, при котором объект собирается из частей, а не получает поведение через жёсткую иерархию.

### Объяснение кода
- `CourseFormat` реализуют `OnlineFormat`, `ClassroomFormat`, `HybridFormat`.
- `PaymentPolicy` реализуют `FreePayment`, `FixedPayment`, `SubscriptionPayment`.
- `CourseInfo` хранит `title`, `CourseFormat format`, `PaymentPolicy payment`.
- `describe()` собирает строку из `title`, `format.describe()` и `payment.describe()`.
- В `Main` показаны готовые комбинации, затем через анонимные классы добавлены формат `intensive` и оплата `hourly`.
- `CourseInfo` при этом не меняется.

**Подробнее по шагам.**
1. Формат и оплата — две независимые оси. Формат отвечает за способ проведения курса, оплата — за способ расчёта.
2. `CourseInfo` содержит по одной ссылке на каждую ось. Это композиция.
3. При вызове `describe()` он делегирует работу формату и оплате, а сам только собирает результат.
4. Если бы использовалось наследование, понадобились бы классы вроде `OnlineFreeCourse`, `OnlineFixedCourse`, `OnlineSubscriptionCourse` и так далее для каждой пары.
5. При трёх форматах и трёх оплатах это 9 классов. При композиции — 3 класса форматов и 3 класса оплат, всего 6.
6. Новый формат или оплата добавляется отдельным классом, и `CourseInfo` не нужно менять.

**Почему анонимные классы.** В `Main` они показывают, что для нового варианта не обязательно создавать именованный файл. Но в реальном проекте чаще делают обычные классы, чтобы код был читаемее.

### Что могут спросить и как отвечать
**Сколько классов было бы при наследовании?**
Для `n` форматов и `m` оплат понадобилось бы `n × m` классов. Для 3 и 3 это 9 классов.

**Почему композиция лучше?**
Она позволяет комбинировать независимые оси без взрыва количества классов и без изменения `CourseInfo` при добавлении нового формата или оплаты.

**Как добавить новый формат или оплату?**
Создать новый класс, реализующий `CourseFormat` или `PaymentPolicy`, и передать его в `CourseInfo`. Код `CourseInfo` менять не нужно.

**Зачем здесь анонимные классы?**
Они показывают расширяемость без отдельного именованного класса. Это удобно для демонстрации, но в продакшене обычно используют обычные классы.

**Что такое «композиция вместо наследования»?**
Это подход, при котором объект содержит другие объекты и делегирует им работу, вместо того чтобы наследовать всё их поведение и комбинировать классы вручную.

### Построчный разбор кода

Ключевые файлы: `CourseFormat.java`, `PaymentPolicy.java`, `CourseInfo.java`, `OnlineFormat.java`, `FixedPayment.java`, `Main.java`.

```java
public interface CourseFormat {                         // 1
    String describe();                                  // 2
}                                                       // 3

public interface PaymentPolicy {                        // 4
    String describe();                                  // 5
}                                                       // 6

public class CourseInfo {                               // 7
    private final String title;                         // 8
    private final CourseFormat format;                  // 9
    private final PaymentPolicy payment;                // 10

    public CourseInfo(String title, CourseFormat format, PaymentPolicy payment) { // 11
        this.title = title;                             // 12
        this.format = format;                           // 13
        this.payment = payment;                         // 14
    }                                                   // 15

    public String describe() {                          // 16
        return title + " [" + format.describe()         // 17
            + ", " + payment.describe() + "]";          // 18
    }                                                   // 19
}                                                       // 20

CourseInfo[] courses = {                                // 21
    new CourseInfo("Java Basics", new OnlineFormat(), new FreePayment()), // 22
    new CourseInfo("Algorithms", new ClassroomFormat(), new FixedPayment(10000)), // 23
    new CourseInfo("System Design", new HybridFormat(), new SubscriptionPayment(1500)) // 24

```

3. `}` — конец интерфейса формата.
4. `PaymentPolicy` — вторая независимая ось: политика оплаты.
5. `describe` — контракт оплаты; формат и оплата не знают друг о друге.
6. `}` — конец интерфейса оплаты.
7. `CourseInfo` — курс, который содержит обе оси через композицию.
8. `title` — общее поле курса.
9. `format` — ссылка на формат; можно подставить любую реализацию.
10. `payment` — ссылка на оплату; можно подставить любую реализацию.
11. Конструктор принимает три независимых части.
12. Сохраняет название.
13. Сохраняет выбранный формат.
14. Сохраняет выбранную политику оплаты.

## Задание 15. Расширяемый движок правил

### Условие
Построить движок правил зачисления: правила — открытая иерархия, результат — закрытая `sealed`-иерархия. Поддержать композитные правила `allOf`/`anyOf`, которые сами являются правилами и могут вкладываться друг в друга.

### Теория
- **Открытая иерархия правил:** новые правила добавляются новыми классами, сервис не меняется.
- **Закрытая иерархия результата:** `sealed`-тип `RuleResult` с вариантами `Passed` и `Failed`.
- **Композитный паттерн:** `AllOfRule` и `AnyOfRule` реализуют тот же интерфейс `EnrollmentRule`, что и простые правила.
- `AllOfRule` останавливается на первом отказе, `AnyOfRule` — на первом успехе.
- `EnrollmentService` зависит от интерфейса правила и обрабатывает результат через `switch` без `default`.
- **Короткое замыкание** — прекращение проверки, как только результат уже известен.

### Объяснение кода
- `EnrollmentRule` — интерфейс с `RuleResult check(long studentId, int studentAge, long courseId)`.
- `RuleResult` — `sealed interface` с `Passed` и `Failed`; оба содержат причину и реализуют `isPassed()`/`reason()`.
- Простые правила:
  - `AgeRule` проверяет минимальный возраст;
  - `CapacityRule` проверяет наличие мест и умеет `enrollOne()`;
  - `DomainRule` проверяет `studentId > 0`;
  - `CourseActiveRule` проверяет `courseId > 0`;
  - `AlwaysFailRule` всегда возвращает отказ.
- Композиты:
  - `AllOfRule` хранит список правил и возвращает первый `Failed`;
  - `AnyOfRule` возвращает первый `Passed`, иначе последний отказ.
- `EnrollmentService` хранит `private final EnrollmentRule rule`, вызывает `rule.check`, разбирает результат через `switch` и печатает `OK:`/`NO:`.
- В `Main` показаны базовый набор, вложенный `AnyOf` и правило с изменяемым счётчиком мест.

**Подробнее по шагам.**
1. `EnrollmentService` получает правило через конструктор и хранит его как `EnrollmentRule`. Сервис не знает, простое это правило или композит.
2. При `enroll` сервис вызывает `rule.check(...)` и получает `RuleResult`.
3. Через `switch` по `RuleResult` он определяет, успех это или отказ, и печатает `OK:` или `NO:`.
4. `AllOfRule` проходит по списку правил. Если очередное правило вернуло `Failed`, он сразу возвращает этот отказ, не проверяя остальные.
5. `AnyOfRule` проходит по списку и возвращает первый `Passed`. Если все правила вернули отказ, он возвращает `Failed` с причиной последнего отказа.
6. `AllOfRule` и `AnyOfRule` сами реализуют `EnrollmentRule`, поэтому их можно вкладывать друг в друга.

**Почему это расширяемо.** Новое правило — это новый класс, реализующий `EnrollmentRule`. `EnrollmentService`, `AllOfRule` и `AnyOfRule` менять не нужно.

### Что могут спросить и как отвечать
**Почему правила — открытая иерархия, а результат — закрытая?**
Правила должны легко расширяться новыми проверками. А результат — это фиксированный набор исходов (`Passed`/`Failed`), который удобно обрабатывать исчерпывающим `switch`.

**Что такое композитный паттерн?**
Это когда объект реализует тот же интерфейс, что и его составные части, и содержит их внутри. `AllOfRule` и `AnyOfRule` — композиты: они сами правила и хранят список правил.

**Как работает короткое замыкание в `AllOfRule`?**
Он проверяет правила по порядку и возвращает первый `Failed`, не вызывая оставшиеся правила. Это экономит работу и сохраняет причину первого отказа.

**Чем `AnyOfRule` отличается от `AllOfRule`?**
`AllOfRule` требует, чтобы прошли все правила. `AnyOfRule` требует хотя бы одно успешное правило и останавливается на первом успехе.

**Как добавить новое правило?**
Создать класс, реализующий `EnrollmentRule`, и передать его в сервис или в композит. Существующий код менять не нужно.

**Почему `EnrollmentService` не знает о конкретных правилах?**
Он зависит только от интерфейса `EnrollmentRule`. Это позволяет подставлять любые правила и композиты без изменения сервиса.

## Краткая шпаргалка

- **Полиморфизм** — один вызов, разные реализации через общий тип.
- **Интерфейс** — контракт и роль, много реализаций, множественное наследование.
- **Абстрактный класс** — общее состояние и общий код, одно наследование.
- **Override** — выбор по динамическому типу; **overload** — по статическому типу и аргументам.
- **Композиция** лучше наследования, когда функции комбинируются.
- **LSP** — наследник не должен ломать ожидания родителя.
- **ISP** — лучше несколько узких интерфейсов, чем один широкий.
- **`equals`/`hashCode`** — согласованы; для наследования опасен `instanceof`, надёжнее `getClass()` или композиция.
- **`sealed` + `switch` без `default`** — компилятор проверяет полноту.
- **Стратегия, декоратор, композит** — три разных способа заменить жёсткие `if`/наследование композицией.
- **Open/Closed** — код открыт для расширения, но закрыт для изменения.

### Построчный разбор кода

Ключевые файлы: `EnrollmentRule.java`, `RuleResult.java`, `Passed.java`, `Failed.java`, `AllOfRule.java`, `EnrollmentService.java`, `Main.java`.

```java
public interface EnrollmentRule {                                   // 1
    RuleResult check(long studentId, int studentAge, long courseId); // 2
}                                                                   // 3

public sealed interface RuleResult permits Passed, Failed {         // 4
    boolean isPassed();                                              // 5
    String reason();                                                 // 6
}                                                                   // 7

public final class Passed implements RuleResult {                   // 8
    public boolean isPassed() { return true; }                      // 9
    public String reason() { return reason; }                       // 10
}                                                                   // 11

public class AllOfRule implements EnrollmentRule {                  // 12
    private final List<EnrollmentRule> rules;                       // 13

    public RuleResult check(...) {                                  // 14
        for (EnrollmentRule rule : rules) {                         // 15
            RuleResult result = rule.check(...);                    // 16
            if (!result.isPassed()) {                               // 17
                return result;                                      // 18
            }                                                       // 19
        }                                                           // 20
        return new Passed("all rules passed");                      // 21
    }                                                               // 22
}                                                                   // 23

public boolean enroll(...) {                                        // 24
    RuleResult result = rule.check(...);                            // 25
    String description = switch (result) {                          // 26
        case Passed p -> "OK: " + p.reason();                       // 27
        case Failed f -> "NO: " + f.reason();                       // 28
    };                                                              // 29
    return result.isPassed();                                       // 30
}                                                                   // 31
```

1. `EnrollmentRule` — открытый контракт правила; сервис зависит только от него.
2. `check` — принимает данные студента и курса, возвращает результат проверки.
3. `}` — любое новое правило можно добавить, не меняя сервис.
4. `sealed interface RuleResult` — результат имеет ровно два варианта.
5. `isPassed` — единый способ узнать, прошло ли правило.
6. `reason` — текстовое объяснение результата.
7. `}` — иерархия закрыта, случайных результатов быть не может.
8. `Passed` — успешный результат правила.
9. `isPassed()` возвращает `true`; это конкретное поведение варианта.
10. `reason()` возвращает сохранённую причину; поле и конструктор `Passed` в фрагменте опущены, в полном классе они есть.
11. `}` — конец `Passed`; `Failed` устроен так же, но `isPassed()` возвращает `false`.
12. `AllOfRule` — композитное правило, которое содержит другие правила.
13. `List<EnrollmentRule>` — внутри могут лежать любые реализации, включая другие композиты.
14. `check` проверяет все вложенные правила по порядку.
15. Цикл по правилам; порядок правил задаёт порядок проверок.
16. `rule.check(...)` — dynamic dispatch вызывает конкретное правило.
17. `!result.isPassed()` — если правило не прошло, дальше проверять нет смысла.
18. `return result` — возвращаем первый отказ; это короткое замыкание.
19. `}` — конец ветки отказа.
20. `}` — конец цикла; сюда попадаем, только если все правила прошли.
21. `new Passed(...)` — общий успешный результат композита.
22. `}` — конец `check`.
23. `}` — конец `AllOfRule`; `AnyOfRule` аналогичен, но возвращает успех при первом `Passed`.
24. `enroll` — клиентский метод сервиса.
25. `rule.check(...)` — сервис не знает, простое это правило или композит.
26. `switch (result)` — разбирает sealed-результат без `default`.
27. `case Passed p` — успешный вариант.
28. `case Failed f` — отказ с причиной; компилятор проверяет полноту.
29. `};` — конец switch.
30. `result.isPassed()` — итоговый boolean для вызывающего кода.
31. `}` — конец метода; сервис не меняется при добавлении новых правил.
